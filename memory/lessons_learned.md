# 实战避坑经验与知识沉淀 (Lessons Learned & Troubleshooting)

本文档记录在工程运转与智能体交互中排查出的系统特性、隐性契约以及踩坑经验，帮助智能体跨越“单会话局限”，避免在后续任务中重复踩坑。

---

## 💡 核心经验与避坑条目

### 1. 【会话重命名】侧边栏标题更新的 RPC 机制
- **踩坑现象**：会话进行多轮后，侧边栏标题依然显示为用户最初输入的第一句话，规范的 `[分类编号][难度分] 概述` 没有生效。
- **底层根因**：DSH 客户端默认抓取首句作为本地暂存标题。后端的 `session.rename` 是独立的 HTTP RPC 路由（`POST /api/session.rename`），如果不主动发送该 RPC，侧边栏永远不会自动改名。
- **避坑对策**：
  - 新任务首轮交互在【定标】阶段必须立即调用 `./scripts/rename_session.sh`；
  - 脚本内部构造 `{ "type": "client-request", "method": "session.rename", "payload": { "sessionId": "...", "title": "..." } }` 并发送给 `$DSH_WEB_URL`，返回 `ok: true` 即可强一致锁定。

---

### 2. 【多模态视觉】`read_image` 工具调用权限与门禁放行
- **踩坑现象**：调用 `read_image` 时系统提示模型或环境不支持图片输入。
- **底层根因**：DSH 宿主对多模态有前置检查门禁，必须在宿主配置文件 `$DSH_HOME/settings.yaml` 的模型定义中明确声明 `input: [text, image]`，宿主才会将图片对象注入模型调用链。
- **避坑对策**：在初始化或遇到多模态失败时，核查宿主 `settings.yaml` 中对应模型节点的 `input` 数组，切勿盲目安装第三方 Python/Node 图像库。

---

### 3. 【文件操作规范】杜绝 Shell cat 盲读与直接覆盖
- **踩坑现象**：直接使用 `write` 工具全量写入已有文件，导致部分未关注代码或历史注释被抹掉。
- **避坑对策**：
  - 严格遵守“先 read 再 edit”的铁律；
  - 查看大文件使用 `read`（带 limit/offset），绝不使用 `cat` 命令；
  - 局部修改必须使用 `edit` 给出唯一的 `old_string`；新建全新文件才使用 `write`。

---

### 4. 【任务分类与概述长度】严格遵守 8 字以内规约
- **踩坑现象**：任务标题写成 `[R001][70分] 针对谷歌搜索引擎模型的研究与落地实践`，字数过多导致 Web GUI 侧边栏截断变形，甚至遮挡时间戳。
- **避坑对策**：
  - 概述文字严格限制在 **8 个汉字以内**（如 `[R001][70分] 谷歌引擎类比模型`）；
  - 分类编号规范使用单字母（R/F/D/S/O/Q）配合三位数字。

---

### 6. 【界面渲染红线】严禁输出裸 HTML 标签（如 details/div/summary）
- **踩坑现象**：在助手回复中写入 `<details>`、`<summary>` 或 `<div style="...">` 试图实现折叠与吸顶，结果界面直接原样打印出了一大段丑陋的 HTML 源代码。
- **底层根因**：DSH 前端聊天渲染引擎（`MarkdownText` 原语）遵循严格的 GFM 不受信内容策略（Untrusted Content Policy），对所有裸 HTML 标签直接作为纯字符串文本输出，绝不会解析为真实的 DOM 节点。
- **避坑对策**：
  - **严禁使用裸 HTML**：彻底杜绝任何 `<div>`、`<details>`、`<summary>`、`<span>` 等原生 HTML 标签；
  - **图形化组件一律改用 GFM 原生语法构建**：使用 Markdown 引用语法 `> ` 配合高辨识度图形图符、水平分割线 `┈┈┈`、代码胶囊与任务清单复选框，DSH 会将其 100% 正确渲染为带有左侧主题色条、独立背景与精致边框的**原生 GUI 图形化卡片组件**。

---

### 7. 【交付闭环】自动化测试真实命令跑通与 100% 绿灯铁律
- **踩坑现象**：智能体写完功能后在思考中声明“代码逻辑完备，符合全部要求”，但实际运行报错或边界用例失效，被用户当场退回。
- **底层根因**：模型在生成代码时存在“乐观偏见 (Optimistic Bias)”，容易忽略真实运行时的语法报错、路径差异与并发边界。
- **避坑对策**：
  - 严格遵守 `rules/coding/testing_and_quality_gate.md`；
  - 必须编写自动化测试用例，并在沙箱中通过 bash 工具真实执行；
  - 交付时必须贴出真实的测试输出回执（exit code 0、100% pass），任何单点失败均阻断结项。

---

### 8. 【工程沉淀】页面视觉台账与前置风险揭示的双重防线
- **踩坑现象**：多轮对话后用户提出“改一下之前的界面”，由于没有唯一命名或截图，智能体常常改错页面或组件；或者接到任务直接改文件导致意外破坏。
- **底层根因**：自然语言描述页面具有极高的模糊性与歧义性；直接动手缺乏缓冲，导致不可逆损失。
- **避坑对策**：
  - 前端工程必须建《项目页面台账》（`P-001`、`P-002`），页面截图按四段式规范命名，后续需求以编号精确指代；
  - 复杂任务动手前强制输出《前置风险评估卡》，凡高危破坏性操作必前置阻断预警。

---

### 9. 【Swift 工具链】仅装 Command Line Tools 时 SwiftUI 与 XCTest 双双不可用
- **踩坑现象**：macOS 上编写 SwiftUI 界面后编译报错 `external macro implementation type 'SwiftUIMacros.StateMacro' could not be found for macro 'State()'; plugin for module 'SwiftUIMacros' not found`；测试代码 `import XCTest` 报 `unable to resolve module dependency: 'XCTest'`。
- **底层根因**：未安装完整 Xcode、仅有 Command Line Tools 时：
  1. `usr/lib/swift/host/plugins/` 下只有 `libObservationMacros.dylib`、`libSwiftMacros.dylib` 与 `testing/`，**不存在 `SwiftUIMacros` 插件**，而此 SDK 中 `@State`/`@Binding`/`@Observable` 等已全部改为宏实现，故 SwiftUI 在该环境下**根本无法编译**（全盘搜索亦无该插件）；
  2. 工具链**不随附 XCTest**，但随附 swift-testing（`Testing.framework` 位于 `Library/Developer/Frameworks`）。
- **避坑对策**：
  - 动手前先探测环境：`ls usr/lib/swift/host/plugins/`、`xcrun --find swift-frontend`；
  - 无完整 Xcode 时，桌面界面改用 **AppKit + WKWebView + 内置 HTML/CSS/JS 前端**，
    该方案零依赖、无需 Node 构建链，且编译实测可用；
  - 单元测试统一使用 **swift-testing**（`import Testing` + `@Test`/`@Suite`/`#expect`），
    不要照搬 XCTest 写法。

### 10. 【SPM 测试】增量编译漏传测试宏插件路径导致误报失败
- **踩坑现象**：首次 `swift test` 全绿，第二次（增量）起突然报 96 处
  `external macro implementation type 'TestingMacros.TestDeclarationMacro' could not be found … plugin for module 'TestingMacros' not found`。
- **底层根因**：SPM 在**增量** emit-module 步骤中未自动附加 `-plugin-path`，导致宏插件目录未进入编译参数（首次全新构建反而正常）。
- **避坑对策**：
  - 显式传入插件路径：`swift test -Xswiftc -plugin-path -Xswiftc "$PLUGIN_DIR"`；
  - `$PLUGIN_DIR` 动态探测更稳：`$(dirname $(xcrun --find swift-frontend))/../lib/swift/host/plugins/testing`，避免硬编码路径在他人机器上失效；
  - 门禁脚本须检查最终是否出现 `Test run with … passed` 摘要且无 `✘`/`error: `，否则判失败（防止「零测试也算通过」）。

### 11. 【视觉台账】`screencapture` 受 TCC 隐私门禁拒绝，应改用应用内渲染快照
- **踩坑现象**：`screencapture -x full.png` 返回 `could not create image from display`；
  指定区域 `screencapture -x -R x,y,w,h` 返回 `could not create image from rect`。
- **底层根因**：macOS 对屏幕录制实行 TCC 隐私授权，未授予终端/宿主「屏幕录制」权限时，
  两种截图方式**都会失败**（报错文案不同，极易被误判为坐标算错）。
- **避坑对策**：
  - 不要反复调坐标或怀疑分辨率，先识别为权限问题；
  - **GUI 页面台账改用应用内的渲染快照**（如 `WKWebView.takeSnapshot`）：
    不需要任何系统权限、只含页面内容无桌面干扰、窗口尺寸可固定使出图可复现；
  - 为截图设计可复现入口：用环境变量固定窗口矩形（如 `KEYINJECTOR_WINDOW_RECT="x,y,w,h"`）
    并让应用在**设置了该变量时不自动居中**，否则窗口位置会被 `center()` 覆盖导致取景漂移。

### 12. 【SVG 出图】`qlmanage` 对细长比例 SVG 会非等比拉伸，必须走 WebKit 精确渲染
- **踩坑现象**：1120×1560 的信息图用 `qlmanage -t` 出图后文字横向溢出卡片、画面被拉伸变形；
  改用 `sips` 裁剪"校正"后反而更糟，且 `sips --cropToHeightWidth` 在本机实测**完全不生效**（输出尺寸不变）。
- **底层根因**：`qlmanage -t -s N` 输出的是 **N×N 正方形缩略图**，对非正方形 SVG 会做非等比适配；
  观察实测：1120×1560 的图在 1600×1600 缩略图里，横向 1:1、纵向约 1.45 倍拉伸（画面上看是"文字变大"）。
- **避坑对策**：
  - 手写 SVG 出 PNG 一律用 `python3 scripts/generate_image.py --svg <文件.svg>`（内部走 `scripts/svg2png.sh`），
    它用系统 WebKit 按 `width/height` 精确渲染，实测输出 1120×1560 与设计完全一致；
  - 校验图形是否溢出时，**不要**依赖缩略图观感，直接用精确渲染结果逐段核对；
  - 若只想看某一局部，可临时把 `viewBox` 改成局部区域再渲染，比裁剪图片更可靠。

### 13. 【流程管控】"必须"与"有判定手段"必须成对出现，否则约束会退化成口号
- **踩坑现象**：规则里写着"十六步全部必须、禁止跳步"，但门禁脚本实际只判定 4 项；
  结果是没被脚本覆盖的工序长期无人执行，而检查看板依旧显示 100% 通过。
- **底层根因**：约束的可执行性 = 有没有客观判定手段。没有命令能验证的"必须"，既检查不了也无法追责，
  还会让整块看板失去公信力（"全绿但没做"）。
- **避坑对策**：
  - 每条流程条款必须绑定一个**真实存在且能跑通的判定命令**，否则降级为"建议"而不是"必须"；
  - 计数口径（条款数、步数、自检项数）只允许一个权威出处，其余文件引用不复述，避免数字漂移；
  - 为流程补上判定脚本后，再把该条从"建议"升回"强制"，形成单向升级通道。

### 14. 【宿主配置】改 `settings.yaml` 前必须先在源码里核实键名与 schema 允许集合

- **踩坑现象**：想解除模型的输出长度上限，直觉是"在模型条目下加个字段"，但字段名究竟叫
  `max_tokens`、`maxTokens` 还是 `maxOutputTokens`，靠猜必然写错；而宿主对配置是
  **命名空间级校验**，一旦非法就整段配置被拒、该 provider 下所有路由静默失效。
- **底层根因**：默认值不在配置里，而在适配器源码常量中。实测 `@deepseek-ai/dsh-llm-pi-ai`
  的 `DEFAULT_MAX_TOKENS = 32768`（`lib/index.js:851`），因为全局 `settings.yaml` 从未配置过
  token 字段，所以所有模型实际都在用这个默认值；可配的两处分别是
  `profile.defaultMaxTokens`（provider 级）与 `modelFields.maxTokens`（模型级），
  取值链路为 `entry.maxTokens ?? base?.maxTokens ?? request.defaultMaxTokens`。
- **避坑对策**：
  - 改配置前先从源码抄出 schema 的允许键集合，逐一比对，**不要凭记忆写字段名**；
  - 注意 `z.object()` 默认会**静默剥离**未声明字段（如既有配置里的 `output: [text, image]`
    就被剥离且不报错），所以"没报错"不等于"字段生效"；
  - 改完用宿主自带的解析器做一次等价的 schema 校验（`success=true`），并跑 diff 确认只改了预期行；
  - 配置改动**必须重启宿主才生效**，重启前只能声称"配置已合法落盘"，不能声称"已生效"。

### 15. 【文本统计】`wc -m` 在命令替换中会退化成字节计数，`bash` 又吃掉前导零

- **踩坑现象**：给脚本加"汉字数 ≤ 8"校验后，所有正常标题全被误判为"不含汉字"；
  另一处正则明明允许 `[0-9]{3}`，传入 `008` 却让 `(( ))` 直接报错。
- **底层根因**：
  1. `LC_ALL=... wc -m` 写在命令替换里时，locale 传递并不可靠，实测**退化为按字节计数**
     （7 个汉字得到 21），于是"字符数 − 字节数"算成负数，误判为中文字数为 0；
  2. bash 的算术求值把带前导零的数字当**八进制**解析，`008`、`009` 属非法八进制字面量，直接抛错。
- **避坑对策**：
  - 统计汉字一律用 `perl -CSD -ne 'my $c = () = $_ =~ /\p{Han}/g; print $c'`，
    这是真正的 Unicode 属性匹配，不受 locale 影响；并在脚本中显式检测 perl 缺失时**报错而非静默通过**；
  - 凡是数值比较，统一写 `(( 10#$VAR < N ))` 强制十进制，杜绝前导零陷阱；
  - 校验类脚本必须**正反例成对实测**（本次 12 反例 + 7 正例），只测正例发现不了"全部误拒"这类致命缺陷。

### 16. 【会话存储】标题与正文都不在明面上，且直接改文件会被覆盖

- **踩坑现象**：要给存量会话批量改名，先找不到标题存哪；找到后又发现直接改文件
  会被运行时覆盖回滚；读会话正文时 `.zstd` 只解出几行，看不到真实对话。
- **底层根因**（四项，全部实测复现）：
  1. **标题权威存储在** `$DSH_HOME/storages/session_projcache.json`
     → `tables.sessions.<sessionId>.rows.title.val`，**不在**会话目录里；
  2. **正文是多帧 zstd**：`session.jsonl.zstd` 由**帧拼接**而成（实测一个 906KB 文件含
     **1623 帧**，每帧对应一次追加写入）。单帧解压只拿到会话头，表现为"906KB 文件解出 0KB"；
     必须按魔数 `28 B5 2F FD` 切分后**逐帧**解压，才能得到完整的 1783KB / 2934 行；
  3. **`user/message` 不全是用户输入**：宿主注入的工作区约束提醒同样以 `user/message` 落盘，
     必须用 `data.source.kind === 'user'` 区分，否则会把系统提醒当成用户需求；
  4. **直接改存储文件无效**：运行时持有内存状态，会把自己的版本回写覆盖掉手工修改。
- **避坑对策**：
  - 改标题一律走宿主 RPC `POST /api/session.rename`（本机 `$DSH_WEB_URL`），
    它实测对**非当前会话**同样有效并持久化；
  - **子代理会话改不了名**：未挂 `session-` 前缀的会话由宿主 subagent routing 托管，
    改名会返回 `agent-busy`（"owned by subagent routing"），应识别并单列说明，不要硬试；
  - 复查要**二次确认**：RPC 返回 `ok:true` 后立刻读存储可能撞上缓存竞态而误判"假成功"，
    稍等再读才是真结论；
  - 用文本方式在 JSON 里定位字段极易取错值——实测 `title` 位于 `sessionId` **之前**，
    正向查找会取到**下一个会话**的标题（静默取错比报错更危险），一律改用结构化 JSON 解析。

### 17. 【模型度量】`max_tokens` 会被"推理 token"吃掉，且**测量任务的设计**决定结论对错

- **踩坑现象**：为验证"输出上限提高是否生效"，我设计了一个"把一句话重复 4000 遍"的探针，
  结果模型两次都只输出 **36 / 39 个字符**就结束（`finish_reason=stop`）。
  我一度据此推断"非流式路径存在约 4k 上限"——**这个推断是错的**。
- **真实原因**：`completion_tokens` = **推理 token + 正文 token**，同吃一份 `max_tokens` 预算。
  实测那两轮 `completion=4067/3596`，其中 `reasoning_tokens=4044/3570`（**约 99%**），
  预算是被**推理**吃光的，与"输出上限"无关。换个任务（要求连续写 1200 条结构化数据）后，
  流式实测单次拿到 **38665 token**（推理 6657 + 正文 32008），一举突破旧的 32768 上限。
- **两条可复用教训**：
  1. **别把"任务设计失败"当成"系统限制"**。测长度上限要给一个**模型愿意且能够持续输出**
     的任务；"重复同一句话"这类无意义任务会让模型把预算烧在推理上，测出来的是任务上限而非接口上限。
  2. **流式与非流式要分开看**，且要用**真实调用形态**去测——DSH 走的是流式，
     只测非流式得出的结论不能代表实际体验。
- **附带的量化事实**（供以后估算用）：本机当前链路实测生成速率 **≈362.7 token/秒**，
  首块延迟 0.21 秒；该速率由服务端决定，客户端无法提速。
- **对配置的直接启示**：若某类任务"回复总是很短就被截断"，先看推理占了多少，
  再决定是抬 `max_tokens` 还是换模型，不要直接归因于长度上限。

### 18. 【会话改名】RPC 返回 `ok:true` 不等于已生效——权威存储有 **3~9 秒延迟**

- **踩坑现象**：自动改名实测中，RPC 明确返回 `{"ok":true,"value":{"title":"...","seq":108}}`，
  但**立刻**读 `session_projcache.json` 仍是旧标题，一度判定"改名失败"。
  等待数秒后复查，标题与 seq **都已正确落盘**。
- **量化对照**（同一会话连续两次改名，观察 seq 与可见时刻）：

  | 读取时刻 | 存储中可见的标题 | seq |
  | :--- | :--- | :--- |
  | 第 1 次改名后立刻 | 旧标题 | 旧 |
  | 约 5 秒后 | 第 1 次的新标题 | 108 |
  | 第 2 次改名后立刻 | 仍是第 1 次的新标题 | 108 |
  | 再约 3~5 秒后 | 第 2 次的新标题 | 109 |

  → 写入是成功的，只是**内存态回写磁盘有秒级延迟**。
- **避坑对策**：判定"改名是否生效"必须**轮询权威存储直到标题匹配**
  （本项目实现为 `waitForTitle()`，默认最多等 15 秒），**绝不采信 RPC 的自述**——
  `ok:true` 本身也是一种"自我宣称"，与本项目既有原则一致。
- **附带教训**：不要用"立刻复查"去验证任何异步写入。否则会把成功大量误判为失败，
  进而做出错误的"修复"（本次就一度以为要换接口，实际只需多等几秒）。
