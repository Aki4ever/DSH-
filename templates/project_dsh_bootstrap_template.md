## 🛡️ 审查门禁与反例约束

1. **零集成阻断**：若新项目未勾选任何 DSH 能力且未做合理性说明，在【定标】阶段立即阻断；
2. **拒绝表面集成**：所勾选的 DSH 能力必须具备真实可调用的代码/接口或可执行路径，严禁空挂虚名；
3. **能力反例前置**：在规划接入 DSH 能力时，必须核对该能力的“适用边界”与“反例约束”，杜绝技术选型错位。

## 🧩 三、框架式留白初始化标准 (Architectural Whitespace Standard)

依据元规则第三十三条，新项目在立项初始化阶段必须坚决贯彻**框架式留白**原则：

### 1. 骨架完备，业务留白
- **必须创建的基础骨架**：
  1. `AGENTS.md`：项目级薄入口（声明管控与底层物理锁生效，指针指向规则）；
  2. `README.md`：项目定位、架构契约与启动入口；
  3. `docs/requirements.md`：需求台账插槽（仅登记 REQ-001 骨架初始化）；
  4. `.gitignore` 与 `.gitattributes`：标准过滤与防丢；
  5. 核心代码目录（如 `src/`）与测试目录（`tests/`）：仅保持结构存在并放置契约声明。
- **坚决禁止的过度预制**：
  - ❌ 严禁预制生硬且未经实际需求的业务伪逻辑、假数据库模型或假 API 实现；
  - ❌ 严禁一次性填充大量冗余 Mock 数据或未测试的业务逻辑；
  - ❌ 严禁复制大型僵死模板导致后续产生反向重构和清理成本。

### 2. 标准插槽热插拔 (Extension Slots)
业务接口仅定义接口规范与方法签名（Signature），实现体优雅留空（如抛出 `NotImplementedError` 或标记 `TODO: REQ-xxx Slot`），所有实质业务逻辑留给后续具体的需求台账驱动，以原子步长增量实现。
