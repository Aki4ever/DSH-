## 四、Q4 图形化方案：参考业界做法

### 4.1 直接对标：Agent Skills 规范（Anthropic 官方）

`anthropics/skills`（GitHub 星数 17.7 万）已开放 **Agent Skills** 格式，规范正文在 <https://agentskills.io/specification>。其结构与**本工程现有做法高度同构**：

| 官方规范要求 | 本工程对应物 | 差距 |
| :--- | :--- | :--- |
| 目录含 `SKILL.md` + 可选 `scripts/` `references/` `assets/` | `indexes/` 索引 + `scripts/` + `docs/` + `assets/` | 结构已具备 |
| `description` 必须写清"**做什么** + **什么时候用**" | 快速通道表已有"触发词 + 路由 + 动作目标" | 口径一致 |
| **渐进式披露**：元数据约 100 token → 正文 < 5000 token → 资源按需 | 本工程 `AGENTS.md` 薄入口 + 按需载入顺序 | 方向一致，但**开工最小读取达 36k–38k token**，与"渐进"相悖 |
| 主文件 **< 500 行**，细节移到独立文件 | `docs/requirements.md` **1207 行 / 约 26.7k token** 被要求整份读 | **明显超标** |

**结论**：本工程的"机制"其实就是一个自研 skill 系统，但**没有按规范实现"渐进式披露"与"触发描述"**，这直接导致每次开工成本高、且新人难以入手。

### 4.2 可抄的图形范式（来自业界公开资料）

详见 [`docs/visual_learning_research.md`](visual_learning_research.md)（420 行调研报告，含证据分级与 46 条 URL 逐条校验）。要点：

| 范式 | 出处 | 怎么用在我们的图上 |
| :--- | :--- | :--- |
| **"一图一职责"** | Airflow UI 官方页：Grid 答"跑没过"、Graph 答"为什么没跑"、Gantt 答"花了多久" | 门禁图只答"现在能不能动手"；决策图只答"我该走哪条路" |
| **不重画示意，在真实界面上描边** | GitHub Actions Quickstart：6 条配图 alt 中 5 条含 `orange outline` | 状态图直接把"当前卡点"高亮，不额外画箭头解释 |
| **hover 高亮依赖关系** | GitLab Pipeline editor 的 "Visualize" 页签 | 十六步流水线的"回退路径"可用图注表达 |
| **定位成"帮我过关"，不是"抓我违规"** | AWS Well-Architected 原文："is not an audit mechanism" | 门禁图文案应写"怎么才能过"，而非"你违反了第几条" |
| **流程图的动机是让新人更快上手** | draw.io 官方页 | 与用户"平易近人且易学"诉求一致 |

### 4.3 工具选型（已实测）

| 工具 | 档位 | 依据 |
| :--- | :--- | :--- |
| **SVG（手工/脚本生成）** | **A 档（本工程必选）** | GUI 可直接显示；可脚本化数据驱动；Git 友好 |
| Mermaid | B 档（仅作源文件） | 纯本地可渲染、中文正常、Git 友好（已实测），但**本 GUI 不渲染** |
| draw.io / Excalidraw | C 档 | 视觉好，但 XML/JSON 进 Git 易冲突，且非 GUI 原生显示 |
| ASCII 字符图 | B 档（辅助） | 零依赖、永不乱码，适合"我该走哪条路"的轻量决策树 |

### 4.4 落地方案：三层图形入口

```

   面向   : 每次开工时的自己

第 3 层 · 全景图（静态 SVG，人工维护）
```

## 五之二、本轮（第 3 轮）深挖出的 3 个新缺陷（均已实测复现并修复）

| 编号 | 缺陷 | 复现证据 | 严重性 |
| :--- | :--- | :--- | :--- |
| **E1** | **退出码恒为 0，失败被静默吞掉** | 四道门全没过时 `check`/`badge`/`card` 仍 `exit 0`；调用方（CI、外部流水线）只能看到"命令成功"，无法分辨门禁是否真的通过 | 高——与"判定要能拦住人"直接相反 |
| **E2** | **缺 `gates.conf` 时脚本崩溃且仍返回 0** | 实测：`G4_DUP_PAIRS: unbound variable`，stdout 为空、不写 `status.json`，**退出码仍是 0** | 高——连"没跑成"都无法被发现 |
| **E3** | **中文列宽按"字节数"估算，导致图上文字重叠** | 实测首版图第 3 道门标题与说明文字重叠；根因是 macOS 自带 `awk` **没有 `ord()`**，取字节序失败后被 `\|\|` 兜底静默吞掉，算出的是字节长度 | 中——直接损害"平易近人" |

**修复**：
- E1 → 新增 `finish()`，全部分支按真实门禁结论返回（`0`=全过，`1`=未过或自身失败）；实测真实工程返回 0、虚构未过工程返回 1。
- E2 → seed 补齐 `G4_DUP_PAIRS`、`G4_TOP_DUP_LIMIT` 等缺失键；新增"关键阈值自检"，任一缺失即 `fatal()` 显式非零退出。
- E3 → 改由 `graph_widths()`（Python）计算**显示宽度**（全角=1em、半角≈0.55em），标题与说明各自受列宽上限约束，超长才截断。实测四行列区间全部落在状态列之前。

## 五之四、第 5 轮：`block` 状态可达 + 一处结构性假阳性

### 5.1 `block`（⛔ 硬阻断）真正可达了

**先纠正一个事实**：`block` 并非"没有实现"——`compute_all` 早已支持 `rc=2 → block`，
`mark_of` / `label_of` / 图上配色也都备好了（⛔ / 硬阻断 / 红色）。缺的是**没有任何
`check_*` 真的返回 2**，所以这条路径从未被走到。

**修的是语义错误**：`check_redundancy` 在"检测器不可用"时 `return 1` → `pending`（⏸️ 待前序），
于是**故障被伪装成"还没轮到这一关"**。而两者处置动作完全相反：

| 状态 | 含义 | 该做什么 |
| :--- | :--- | :--- |
| ⏸️ 待前序 | 前序门禁未过，本门禁还没轮到 | 继续做前序 |
| ⛔ 硬阻断 | 检测工具本身坏了 / 结果不可判定 | **立刻修工具** |

已改为 `return 2`。**实测验证**（虚构工程：G1/G2/G3 因骨架不全为"待前序"，冗余检测器报"不可判定"）：

```
| **G4 冗余检测** | ⛔ 硬阻断 | -1 高相似块对 · 0 重复标题 |
```

修复前这里会显示 `⏸️ 待前序`。真实工程实测未误触发，仍为 `4/4`。

### 5.2 表格结构行造成结构性假阳性（本轮第二次撞到真缺陷）

**现象**：改完 5.1 后跑门禁，**本工程从 4/4 掉到 3/4**。

**排查**（先确认因果，不猜）：
- 把新写的文档临时移出 → 单行最高重复 `46 → 38`、门禁回到 4/4；移回 → 又变 46。**确认是本轮新内容触发**。
- 再定位具体行：`| :--- | :--- | :--- |`（Markdown 表格分隔行）全库出现 **47 次**。

**根因**：`substantive_lines()` 过滤了纯符号行，但**没过滤表格结构行**。表格线字符数 ≥ `G4_MIN_LINE_LEN`(12)，
于是被当作"实质行"计入重复度。而它的重复次数**随文档数量线性增长** —— 文档越多越必然超限。
这是**结构性假阳性**：工程越规范（表格越多），门禁越容易误报失败。

**修复**：过滤阶段增加判据"去掉所有表格竖线/横线与空白后，是否还剩字"。
- 实测：单行最高 `46 → 37`（限 45），门禁恢复 `4/4`
- **反向验证**（确保没把真信号一起过滤掉）：喂入 1 个内容行 + 3 种表格线，过滤后**只保留内容行** ✅

> 这处修复的价值不只是"让门禁变绿"：它去掉了一个**会随规模恶化**的误报源。
> 若不修，任何新增带表格的文档都会随机把 G4 顶红，最终必然逼人调高阈值——那才是真的丢了检出能力。

### 5.3 一个值得记下的过程教训

第 3 轮我把门禁跑成 `4/4` 时，**当时的新文档已经让单行指标处在 46 的临界值**，
但那次我恰好没有重跑 `check`（只跑了 `badge`，而 `badge` 用的是 30 秒缓存）。
所以"4/4 通过"这个结论在那一轮**并未被真实复核覆盖**。
本轮因为要验证 `block` 而重跑 `check`，才把它暴露出来。

**教训**：改完任何影响门禁输入的东西（尤其是新增文档），必须跑 `check` 而不是 `badge`
——`badge` 走缓存，`check` 才真算。

## 九、第 6 轮：修复「十七法典」并揪出 C2 检测器长期失灵

### 9.1 那条"已校准"其实是假的

`docs/constraint_mechanism_spec.md` 的 P5 行声称"**已全部校准**：标题计数对齐实际条目"，

### 9.2 修文档很容易，真正的问题是检测器从来没管过这件事

把标题改成「全局元规则二十一条」只需一步，但**验证过程暴露了更严重的事实**：

> 我把标题**故意改回错误值**（先试「十七条」，再试原始的「十七法典」），
> `conflict_scan` **两次都报「冲突 0 项」**。

于是顺藤摸瓜，在 `conflict_scan.mjs` 找到**两个叠加的缺陷**，任一存在都足以让 C2 失效：

| # | 缺陷 | 后果 |
| :-- | :--- | :--- |
| 1 | `COUNT_RULES` 正则写 `元规则.*法典`，而文件标题已变成「…二十一条」（不含"法典"） | 规则失配，该口径**从不进入校验** |
| 2 | `checkCount` 只看 `h.items`，但分层标题下各条目**自身就是标题**（`### 第一条：…`），被记为 `childHeadings` 而非 `items` | 顶层标题 `items` 恒为 **0** → 撞上 `actualItems < 2` 直接 `return null` |
| 3 | 进一步查出 `childHeadings` **被初始化但从未递增**（死字段） | 即便放宽正则，计数依然是 0 |

**这意味着 C2「计数冲突」这条口径自建立起就没有真正生效过**，而它的自检一直是绿的。

### 9.3 修复过程中我自己也错了三次（据实记录）

修 `childHeadings` 时，我连改三版都不对，且每次推演都"看起来对"：

1. 只对**直接父级**递增 → 第二个 `###` 的父级已是第一个 `###`，顶层只增到 **1**；
2. 遍历 `out` 递增 → 处理第一个 `###` 时 `out` **还空着**（顶层 `##` 尚未 flush），顶层得 **0**；
3. 改成 `[...out, current]` 依赖闭包引用生效 → 实测仍只增到 **1**。

三次都在"猜引用语义"。最后改用**后处理**：按数组顺序与层级，一次算清每个标题的作用域内有多少子标题。
最小复现（1 个 `##` + 3 个 `###`）当场验证 → `child=3`；真实文件 → `child=21`。

> 教训记在这里：**推演替代不了实测**。前面三版我都能自圆其说，但都错。
> 真正解决问题的是"最小复现 + 直接打印返回值"，不是继续想。

## 十二、拦截层真实验证与逃生舱死锁修复（六.3 的答案）

### 12.1 六.3 原来是"想当然"，实测推翻了它

六.3 原本写的是"**务必**确认 `./scripts/control_gates.sh check` 始终可用（否则会死锁）"——
一直挂着未验证。这次做了受控实验：把宿主的 `.dsh-control/status.json` 临时改成
`execAllowed: false` 模拟"门禁未过"，然后逐条测行为。

| # | 测试动作 | 结果 |
| :-- | :--- | :--- |
| 1 | `cd "<工程>" && echo x > verify_probe_a.txt` | ⛔ 被拒，探针文件未产生 |
| 2 | bash 重定向写工程内文件 | ⛔ 被拒，文件不存在 |
| 3 | `cd "<工程>" && ./scripts/control_gates.sh check` | ⛔ **被拒**（守卫自己推荐的自救命令）|
| 4 | `/<绝对路径>/scripts/control_gates.sh badge` | ✅ 放行 |

**结论：不是"始终可用"，而是"只在特定写法下可用"。**

### 12.2 根因（`ai-control/plugin/index.mjs`，修复前第 223 行）

```js
if (i === 0 || /^(bash|sh|zsh|node|npx|\.\/|\/)/.test(prev) || prev.endsWith('/')) return true
```

判定逃生舱脚本 token 时，看的是它的**前一个 token**。而
`cd "<工程>" && ./scripts/control_gates.sh check` 里脚本前面是 **`&&`** ——
不在允许列表 → 逃生舱失效。

**这是真死锁，不是理论担忧**：门禁未过时 bash 全被拒，而消息里给的另一条路
（设 `DSH_CONTROL_GUARD=off`）**同样需要 bash**。两条自救路径同时失效。

### 12.3 顺带拿到拦截层(Q1)的真凭实据

这次实验之前，"守卫是否真在工作"只有源码证据。现在有了行为证据：

- `execAllowed: false` 时改动型调用被拒并给出卡点与进度（`2/4`、卡点`需求文档同步`）；
- 只读工具（`read`/`grep`/`glob`）全程可用，与设计一致。

### 12.4 修法：从"看前一个 token"改为"看命令段起始位"

改动集中在 `isEscape` 的 bash 分支：

1. **按 shell 控制符切分命令段**（`&&`、`||`、`;`、`|`、换行），
   且**引号内的控制符不当分隔符**；每个段单独判断；
2. **段首 token 是逃生脚本路径** → 放行（`./scripts/x`、`/abs/.../scripts/x`）；
3. **段首是解释器**（`bash`/`sh`/`zsh`/`node`/`npx`，**取 basename**，因为本机 node
   只有绝对路径可用）且参数含逃生脚本 → 放行；
4. **词法切分尊重引号**：引号内含空格的内容算一个 token ——
   因为本机 node 在 `/Volumes/DSH Desktop/DSH Desktop.app/...`，**路径含空格**；
5. **反例仍然被拒**：`cat scripts/x`、`echo scripts/x`、`cd /tmp && echo scripts/x`、
   `node` 跑非白名单脚本 —— 段首不是解释器或脚本，一律不放行。

### 12.5 修复过程中又发现一个真实缺陷

写用例时发现：`isInterpreter` 原本只比**裸命令名**，于是
`/Volumes/.../runtime/node scripts/redundancy_scan.mjs`（**本机唯一可用的调用形式**）
被判为非逃生舱。已改为取 basename 判定。

> 若不做这一步，`scripts/verify_guard_live.sh` 里"用绝对路径 node 跑自检"这条命令
> 在门禁未过时会被拒 —— 而它恰恰是排查问题时要用的命令。

### 12.6 自检：47 → 56 项，并证明新用例不是走过场
