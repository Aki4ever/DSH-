## 三、精简后的执行需求文案（正式版本）

### 总目标

把散落在多处的流程条款，收敛成**一条流程 = 一个判定点 = 一组可量化证据**的机制，并补上冗余与冲突双检，使机制可被命名、可被指代、可被外人看懂、可自我迭代。

### 机制正式命名（已定名）

| 层次 | 名称 | 代号 | 一句话职责 |
| :--- | :--- | :--- | :--- |
| 整套机制 | **管控机制** | `GCM` | 用磁盘实况决定"能不能动手" |
| 第一层 | **注入层** | `GCM-INJECT` | 只放红线与指针，预算 ≤ 12KB |
| 第二层 | **状态层** | `GCM-STATE` | 只产出 `status.json`，绝不采信自述 |
| 第三层 | **判定层** | `GCM-GATE` | 逐道判定 + 双检（冗余/冲突） |
| 第四层 | **拦截层** | `GCM-GUARD` | 未过门禁就拒绝改动型调用 |

> 命名规则：日常指代用"管控机制 + 层名"（例如"优化判定层的计数口径"）；
> 脚本文件名保持不变（避免破坏既有引用），代号仅供跨语言场合使用。
> **权威出处**：`indexes/rules_index.md` 第〇章；其余文件一律引用不复述别名。

### 需求 1：每个流程都有效执行（精简 + 可验证）

1. **一条流程必须绑定一个判定点**：十六步流水线中的每一步，要么落到 `control_gates.sh` 的可量化判定，要么落到一个独立检查脚本；两样都没有的步骤，**从强制流程降级为建议**，不得再以"必须"表述。
2. **删空话**：删除无法验证的表述（如"严格推进""100% 推行"），改为可执行动作 + 可观测证据。
3. **计数口径唯一**：全库阶段数、步数、条款数只允许一个权威出处，其他文件一律引用不再复述。
4. **流程可控可查**：复用 `scripts/control_gates.sh check` 一条命令打印门禁与证据来源；存量是否跟上则由 `scripts/legacy_align_scan.mjs` 单独回答。

**验收**：给出流程清单表（流程名 / 判定脚本 / 判定命令 / 当前状态），条目无遗漏、无"无主"流程。

### 需求 2：冗余与冲突双检机制

**冗余判定（已有，需纳入标准出口）**

- 判定口径：块级切分 → 归一化 → 词级 Jaccard ≥ 0.85 判为高相似块对。
- 处置规则：**冗余 → 合并为迭代版本**。保留一份权威源，其余改为指针；被合并条目的历史在台账中留痕，不删除记录。
- 现有工具：`node scripts/redundancy_scan.mjs --root .`

**冲突判定（新增）**

- 判定口径分三类，逐类给结论：
  1. **同事实冲突**：同一事实（版本号、计数、路径、阈值）在不同文件取值不一致 → 必须统一；
  2. **同行为冲突**：同一场景给出不同动作（如 A 文说"必须提交"，B 文说"可跳过"）→ 必须裁决；
  3. **优先级冲突**：与 `meta_rules.md` 末尾裁决链、`AGENTS.md` 四级优先级相矛盾的表述 → 以高优先级为准，改低优先级文件。
- 处置规则：**冲突 → 先出裁决方案，再迭代**。裁决方案必须包含：冲突点、双方依据、按现有优先级链的判定结论、可选方案与影响面，**由用户确认后才落改**（遵循"不得自行取舍"红线）。
- 新增工具：`scripts/conflict_scan.mjs`（只读、不改文件），输出冲突清单 JSON + 人类可读报告。

**双检自检要求（不可省）**

- 冗余检测器必须证明"模板不误报"且"复制粘贴必检出"（已有 `--self-test`）。
- 冲突检测器必须证明"真冲突必检出"且"同义不同词不误报"。
- 检测器不可用时，门禁判定为**未通过**，绝不允许"检测失效 = 通过"。

**验收**：两个检测器实跑通过；对 P5 的五处不一致，冲突检测器能自动报出并给出裁决建议。

### 需求 3：命名与指代

**验收**：名称写入 `indexes/rules_index.md`（或新建专门索引），后续对话可用"闸门管控机制 / GCM"直接指代；`README.md`、`AGENTS.md`、`ai-control/README.md` 三处入口表述一致。

### 需求 4：普通人能看懂的信息图

**要求**：

1. 载体：原生 SVG（带 `viewBox`，可自适应），并在 `assets/generated_images/` 留 SVG 与 PNG 两份；
2. 讲清三件事：**什么时候会被拦**、**拦的依据从哪来**、**怎么才能通过**；
3. 用生活化比喻（例如"进厂安检门 + 体检报告 + 保安拦截"），**不出现未解释的专业术语**；
4. 图内所有数字必须来自实跑结果，不得编造；
5. 同时给一段文字版说明（给不看图的人），并在 `docs/` 留指引。

**验收**：找非专业读者试读，能在 1 分钟内说出"四道门闸分别查什么、不通过会怎样"。

### 需求 5：每次更新同时优化存量与新增

1. **存量校准脚本**：新增 `scripts/legacy_align_scan.mjs`（或合入双检器），扫描全库并输出"存量待对齐清单"，检查项至少包括：
   - 各文档头部版本号是否与台账总版本一致；
   - 标题声明的条款数/步数是否与实际条目数一致；
   - 计数类数字（自检项数等）是否与实际一致；
   - 是否残留旧命名（中英混用、旧称）；
   - 是否存在失效的相对链接。
2. **强制同步**：任何一次迭代的收尾，必须让该清单清零，或明确列出未清零项及原因（并在台账留痕）。
3. **遇碰即对齐**：沿用 `meta_rules.md` 第十九条的"遇碰即对齐"原则，本次触及的文件全部按新规范升级。
4. **不许只修声明不修事实**：禁止用改文字的方式掩盖不一致（例如把"23 项"改成"33 项"却不实际跑一次自检）。

**验收**：校准清单清零；台账新增条目并注明本次升版号。

## 四、执行约束（做这件事时必须遵守）

1. **先定标再动手**：本文件经用户确认后，先在 `docs/requirements.md` 登记新条目（下一可用编号为 `REQ-044`），再改文件。
2. **门禁不绕过**：实现过程中如门禁未过，先修门禁再干别的；不得用 `DSH_CONTROL_GUARD=off` 图省事。
3. **冲突不自裁**：凡是需求之间、规则之间冲突，停在冲突点请用户裁决。
4. **写后必读回**：每个被改文件改完立即读回校验。
5. **未验证必声明**：凡是没实跑验证的，收尾明确写"未验证"。
6. **一工程一仓库**：改动收尾需 commit 并 push 到远程；无远程地址时开页引导。
