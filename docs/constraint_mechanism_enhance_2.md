### 需求 2：快速通道机制（注册规范）

**2.1 通道注册表（唯一权威源）**

- 位置：`indexes/shortcuts_index.md`（已有，继续作为唯一权威源）；
- 其他文件只允许写指针，禁止复制通道内容（现状已合规，需保持）。

**2.2 触发词规则**

| 规则 | 要求 |
| :--- | :--- |
| 长度 | ≤ 12 个汉字，力求一眼记住 |
| 唯一性 | 不得与既有通道触发词相同或高度近似（由冲突检测器的新增判定拦住） |
| 同义词 | 允许挂 1~2 个同义说法，写法为"主触发词 +（或"别名"）" |
| 命名偏好 | 动宾结构短语（如"看看管控机制""生成信息图"），避免单字或纯名词 |

**2.3 执行契约（每条通道必须写清四件事）**

1. **路由层级**：G0 高速 / G1 干线 / G2 支线 / G3 辅道；
2. **命中后做什么**：要跑的脚本或要读的文件（必须是真实存在的路径）；
3. **输出什么**：交付物形态（看板 / 清单 / 图片 / 报告）；
4. **落地条件**：目标文件挂成 Markdown 链接，使其成为**可点击、可校验**的指针。

**2.4 注册与退役流程**

- **注册**：按需求 1 的四道审计 → 在通道表新增一行（带可点击链接）→ 台账登记；
- **退役**：目标文件已不存在或功能被合并时，必须删除该行，禁止留死通道；
- **自检**：新增 `scripts/channel_audit.mjs`（通道注册审计器），校验三项：
  1. 通道表里的每个路径真实存在（无死通道）；
  2. 用户的表述是否命中通道表（内置若干常用说法的正例、以及"看似像但不应命中"的反例）；
  3. 触发词是否重复或过度近似。
- **验收**：审计器自带正反例自检全部通过；对现有 20 条通道实扫无死通道。

### 需求 3：新增通道"看看管控机制"

- **触发词**：`看看管控机制`（别名：`管控机制`、`门禁状态`）；
- **路由**：G1 干线；
- **命中后执行**：
  1. `./scripts/control_gates.sh check` —— 取四道门禁实测状态；
  2. `node scripts/conflict_scan.mjs --root .` —— 取冲突检测结果；
  3. `node scripts/legacy_align_scan.mjs --root .` —— 取存量待对齐结果；
  4. `node scripts/redundancy_scan.mjs --root .` —— 取冗余检测结果。
- **输出**：一份"管控机制全貌卡"，必须包含
  1. 四道门禁各自查什么、当前状态、量化指标；
  2. 双检与存量校准的实测数字；
  3. 十六步的强制/建议分级统计；
  4. 当前快速通道清单（触发词一览）；
  5. 机制四层分工与各自落地载体（可点击路径）。
- **硬要求**：输出中的数字必须来自**本次实跑**，不得复述文档里的旧数字。

### 需求 4：新增通道"生成信息图"

- **触发词**：`生成信息图`（别名：`出信息图`、`画机制图`）；
- **路由**：G1 干线；
- **命中后执行（按教学图生成机制走）**：
  1. **选型**：读 `docs/diagram_generation_guide.md` 的技术选型决策树，确定技术方案（本文档场景固定为**原生 SVG**）；
  2. **取料**：确定信息图的主题与数据来源（机制类信息图必须先跑判定命令取实测数据）；
  3. **绘制**：手写 SVG，必须带 `viewBox`，尺寸与 `width/height` 一致；
  4. **栅格化**：`python3 scripts/generate_image.py --svg <文件.svg>`（内部走 `scripts/svg_rasterize.swift` 精确渲染）；
  5. **校验**：渲染后按段落目视核对无文字溢出、无裁切；
  6. **登记**：产物写入 `assets/generated_images/`，并在 `indexes/rules_index.md` 或 `docs/` 相应说明处挂指针。
- **参数化**：支持"生成信息图：<主题>"的形式；主题为"管控机制"时复用已有机制信息图的版式，只更新数据。
- **输出**：SVG 与 PNG 两个文件路径 + 可点击入口。
- **验收**：说这句话后确实产生新的图片文件，且尺寸与设计一致。

## 七、附加需求（用户中途追加）：任务常显在输入框

> 原话："任务无论完成与否都应该常显在输入框上"

**已落地，且不需要自研前端组件** —— DSH 原生就有输入框停靠坞：

| 组件 | 挂载槽位 | 常显条件 |
| :--- | :--- | :--- |
| `TodoPanel` 任务待办条 | `conversation.input.dock`（order=0） | 清单非空即常显（完成态也常显） |
| `GoalBar` 目标条 | `conversation.input.dock`（order=10） | 存在活跃自主目标即常显 |

**唯一失效条件（源码级依据）**：`TodoPanel` 里有一条硬判定 `if (todos.length === 0) return null;`
（`@deepseek-ai/dsh-client-ui-conversation` 客户端代码），且 `todo_write` 的 `content` 必须非空
（`@deepseek-ai/dsh-tool-todo` 校验）—— 结论：**清单在，进度就在；清单空，输入框上方就没了。**

规则已写入 [`rules/workflow/task_execution_flow.md`](../rules/workflow/task_execution_flow.md) 三之一：
开工即建清单（至少一项 in_progress）／收尾保留完成态清单**不得清空**／长任务建目标条，
并给出可执行判定（清单非空 + `get_goal` 返回 active + 空态归因）。
