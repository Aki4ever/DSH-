# 规则更新联动排查与存量资源治理规范 (Audit and Cleanup)

> ### 🏷️ **版本信息与实施追踪**
> - **当前文档版本**：`v4.21.0`
> - **对应实施版本**：`v4.21.0`
> - **文档类型 (Doc Type)**：`[CORE-RULE 核心工作流法典]`
> - **清理定位 (Retention)**：`[PERMANENT 永久核心白名单 · 严禁删除]`
> - **规范层级**：`【工作流 · 资源治理与清理权威法典】`
> - **需求依据**：`REQ-002`、`REQ-051`、`REQ-073`
> - **生效状态**：`[Release 稳定生效]`

本规范用于指导在更新任何规则时，如何对当前工程内的所有已有资源（旧规则、关联文档、模板与示例）进行同步排查与清理，确保规则库始终整洁、统一、无冲突。

---

## 🔍 一、触发条件

只要发生以下任一变动，必须立刻触发存量资源排查：
1. **新增规则**：创建了新的规则文件；
2. **优化规则**：修改了现有规则的内容、判断条件或优先级；
3. **废除规则**：停用某项旧规则；
4. **术语调整**：更新了系统组件命名或操作口令。

---

## 🛠️ 二、排查范围与操作步骤

排查工作分为三步，依次进行：

### 第一步：影响范围全盘检索
- 使用全局搜索工具，搜索受影响规则的：
  - 文件名（例如 `meta_rules.md`）；
  - 核心关键词或被替换的旧词汇；
  - 关联的需求编号（例如 `REQ-002`）。
- 梳理出所有引用该规则的旧文档、模板或脚本。

### 第二步：分类对比与处置

针对找到的每一个存量文件，按以下原则处置：

| 存量资源情况 | 处置动作 | 具体做法 |
| :--- | :--- | :--- |
| **存在冲突或表述不一致** | **立刻同步修改** | 按照最新规则的口径，修改旧文件中的矛盾表述，保持全局一致。 |
| **引用了旧术语或旧路径** | **全局批量替换** | 修正失效的文件链接、废弃的方法名或旧口令。 |
| **整份旧规则已被完全取代** | **标记废弃并归档** | 在文件开头醒目注明 `[已废弃]`，注明替代文件；若确无保留价值则按需清理。 |
| **属于补充说明或衍生案例** | **增量校准** | 确认其边界是否仍符合新规则，补充或校正示例代码。 |

### 第三步：闭环核对与检查
- 检查主目录 `README.md` 是否需要更新目录索引；
- 检查需求文档 `docs/requirements.md` 是否记录了本次联动影响；
- 确保没有残留失效链接或未解决的冲突。

---

## 🧹 三、结构与内容冗余去重与优化机制 (Structure De-duplication & Optimization Protocol)

为了杜绝规则库随着版本演进而变得臃肿庞杂，建立常态化的**冗余去重与结构瘦身机制**：

### 1. 结构去重原则（瘦身与精简）
- **单一权威原则**：同类功能的模板（如 README 模板、卡片模板）或脚本仅保留一份权威源文件，禁止在不同目录下复制衍生多个功能相同的副本；
- **目录精简原则**：禁止创建无明确业务内涵的深层嵌套目录；凡是空目录必须有 `.gitkeep` 占位，长期无用空目录及时清理并在 Git 中同步移除；
- **工具聚合原则**：通用性辅助脚本全部归口至 `scripts/`，接口抽象归口至 `indexes/`，禁止零散脚本随处散落。

### 2. 规则与内容去重原则
- **增量归并，拒绝分裂**：新提出的规则若属于既有规则（如元规则、执行流）的补充，必须合并进已有母文档作为新增章节，严禁拆分成若干破碎的微型规范文件；
- **同义概念合并**：在整个体系中，同一个机制或概念（如会话重命名、吸顶组件、难度打分）必须统一术语与引用锚点，杜绝同义词导致的认知混淆；
- **废弃资源归档**：已被新规范完全覆盖的历史说明，按规则标记 `[DEPRECATED]` 并移动或合并，杜绝存留两条相互冲突的有效指引。

### 3. 去重排查三步法
1. **查重扫描**：在准备新建文件或段落前，使用 `grep` 或 `glob` 全局检索关键词；
2. **重叠合并**：若重叠度高，直接在已有文件中通过 `edit` 增量扩充；
3. **死链与孤岛清理**：更新后立即排查相对路径与文档引用，确保所有超链接可访问。

## 💾 五、周期性硬盘检测与安全清理规范 (Disk Health & Safe Cleanup Protocol)

为防止 DSH 执行过程中临时溢出物过多导致宿主磁盘溢满（如当前使用率达到 90%+ 危险水位），建立常态化周期检测与安全自愈清理机制：

### 1. 周期触发与预警阈值
- **触发时机**：
  - 会话初始化自检（开箱）与任务收尾（归卷）阶段自动运行 `./scripts/disk_check_and_cleanup.sh --auto`；
- **高水线阈值**：
  - 磁盘使用率 $\ge 90\%$ 或可用空间 $< 20\text{ GB}$ 时判定为空间紧张，强制触发安全清扫；
  - 清理完毕后汇报释放字节数与最新可用空间。

### 2. 垃圾清理范围 (Blacklist)
- **宿主临时溢出大文件**：`/tmp` 与 `TMPDIR` 下超过 30 分钟未更新的 `dsh-spill-*`、`dsh-subprocess-*` 溢出目录；
- **工程调试残余文件**：单次调试产生的 `*.tmp`、`*~`、临时测试脚本副本；
- **系统元数据碎片**：工程中自动生成的 `.DS_Store`、`Thumbs.db`；
- **Git 冗余松散对象**：定期执行 `git gc --prune=now --quiet` 压缩回收。

### 3. 🛡️ 绝对禁止删除的有用资产白名单 (Protected Whitelist)
以下资产对任务理解、经验沉淀和后续执行具有关键支撑价值，**无论磁盘多紧张均绝对禁止触碰或删除**：
1. **经验与记忆资产**：`memory/`（上下文偏好、lessons_learned 实战避坑认知、efficiency_audit_log 审计台账）；
2. **业务与技术知识库**：`knowledge/`（所有通用工程规范、专属项目世界观及设定、原生可视化组件法典）；
3. **系统规则与协议**：`rules/`（元规则、工作流、编码、安全基线）；
4. **能力与接口索引**：`indexes/`（全景矩阵、工具清单、快捷通道）；
5. **核心台账与模板**：`docs/requirements.md`、`templates/`、`scripts/` 下正式运维脚本；
6. **活跃会话快照**：`$DSH_HOME/sessions/...` 中各活跃会话持久化历史 `session.jsonl.zstd`。

## 🏷️ 六、全域文件生命周期元数据标记与快速清除定位机制 (File Lifecycle Tagging & Purge Protocol)

为彻底解决临时草稿、中间产物与正式资产混杂导致的“不敢清、清不掉、易误删”顽疾，确立**写时显式标记、巡检即时定位、超期/超水安全清除**的全生命周期规约：

### 1. 文件头部元数据标记标准语法 (Metadata Tagging Header)

在系统内任何新建、生成的受管文档（Markdown、代码、配置、报告）顶部，必须包含标准化的元数据引用块：

```markdown
> ### 🏷️ 资产元数据与生命周期标记
> - **文档类型 (Doc Type)**: `[CORE-RULE / KNOWLEDGE / REQUIREMENT / MEMORY / SCRATCHPAD / REPORT / TEST-ARTIFACT]`
> - **清理定位 (Retention)**: `[PERMANENT / PERSISTENT / EPHEMERAL-AUTO / DEPRECATED-PURGEABLE]`
> - **生成会话**: `[优规013][45] 严守管控文件标记`
> - **到期/清理条件**: `[会话结束即删 / 30天后归档 / 永久保留 / 随版本替代清理]`
```

### 2. 四大保留与清除定位等级 (Retention Policy Matrix)

| 标记级别 | 策略全称 | 核心语义与定位 | 清理定位与处置动作 | 适用范围典型代表 |
| :---: | :--- | :--- | :--- | :--- |
| **`[PERMANENT]`** | **永久核心资产** | 系统元规、核心知识库、主需求台账与持久记忆 | **绝对禁止物理删除**。清理脚本若扫到直接跳过并保护。 | `rules/`、`knowledge/`、`docs/requirements.md`、`memory/` |
| **`[PERSISTENT]`** | **长期受管资产** | 正式设计方案、架构图文案、系统索引与正式模板 | **受控版本归档**。禁止日常自动清理，废弃需走版本流程。 | 正式设计文档、架构基线、正式测试套件 |
| **`[EPHEMERAL-AUTO]`** | **临时易失产物** | 会话草稿、单次排查结果、调试输出、调试脚本 | **自动清理机制可定位直接删除**。无需人工二次确认。 | 会话临时草稿、中间导出的测试报告副本、测试中间件 |
| **`[DEPRECATED-PURGEABLE]`** | **已废弃可清理** | 已被新版本文档完全取代且已归档的历史残留 | **批量安全清除**。巡检或磁盘紧张时由清理脚本直接 purge。 | 历史迁移废弃文件、失效备份副本 |

### 3. 清除机制快速扫描与自动化联动规约

自动化磁盘自愈清理脚本（[`scripts/disk_check_and_cleanup.sh`](../../scripts/disk_check_and_cleanup.sh)）在执行 `--clean` 或 `--auto` 时：
1. **秒级正则检索**：使用正则 `Retention:\s*\[(EPHEMERAL-AUTO|DEPRECATED-PURGEABLE)\]` 扫描工作区文件；
2. **白名单双重保护**：即使文件内包含可清理标记，只要位于 `rules/`、`knowledge/`、`memory/` 等核心白名单目录中，依然受物理白名单保护拒删；
3. **无标记文件保守策略**：未标记生命周期的存量文件默认判定为 `[PERSISTENT]`，严禁盲目删除，必须先做人工确认或版本排查。
