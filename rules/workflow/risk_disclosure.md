# 任务前置风险揭示与评估规范 (Pre-flight Risk Disclosure Specification)

> - **对应实施版本**：`v3.4.0`

本文档确立了工程内所有任务在动手执行前必须遵循的**前置风险揭示与应对预案规范**。凡谋先审险，凡动必有备，彻底杜绝无预警破坏性操作与执行盲区。

---

## 🧭 一、核心原则与触发时机

### 1. 核心原则
- **不声明不行动**：未经明确的风险揭示与边界评估，禁止对任何代码、配置或业务文件进行物理写入或破坏性变更；
- **真实量化拒套话**：严禁无脑输出空洞套话，风险评估必须与当前任务的技术栈、目标文件、影响拓扑精准对应；
- **兜底方案必前置**：揭示风险的同时，必须给出发生最坏情况时的降级或回滚预案。

### 2. 触发时机与轨道分流
- **标准完备流 (Standard Track · 难度 > 35分)**：必须在【三、筹策】阶段（S07/S08）显式输出《前置风险评估卡》，作为进入【四、攻坚】编写的硬性前置门禁；
- **快速轻量流 (Fast Track · 难度 ≤ 35分)**：可在规划思路中以 1~2 句话简要标注轻量风险及影响范围，确保快速敏捷同时不失防线。

## 🛡️ 二、四维风险雷达评估模型

智能体在执行任务前，必须依序扫描以下四个维度：

```text
               ┌── 1. 技术依赖与环境风险 (Runtime / Dependency)
               ├── 2. 数据与代码破坏性风险 (Data Loss / Destructive Overwrite)
[四维风险雷达] ──┤
               ├── 3. 需求边界与业务侧漏风险 (Boundary Creep / Breaking Change)
               └── 4. 权限、网络与安全红线风险 (Security Baseline / Sandboxing)
```

| 风险维度 | 重点评估要点 | 典型高危场景 | 兜底与防护手段 |
| :--- | :--- | :--- | :--- |
| **1. 技术依赖与环境风险** | 运行时环境变更、三方包安装、全局环境变量污染、版本不兼容 | 安装全局 npm/pip 包、升级核心底层框架版本 | 优先采用项目本地锁定依赖，记录原版本号备查 |
| **2. 数据破坏性与不可逆操作** | 文件覆盖、数据库迁移修改、目录删除、重命名遗失 Git 追踪 | 大面积覆写文件、`rm -rf` 批量清理、数据库 Drop 表 | 严格执行写前指纹读取、保留备份分母、小步原子提交 |
| **3. 需求边界与业务冲突** | 需求语义模糊、修改核心公共模块引发联锁破坏、世界观跨项目污染 | 修改通用公共基类影响其他子系统、将游戏规范带入通用工具 | 圈定最小修改边界 (Blast Radius)，前置查阅知识库 |
| **4. 权限与安全红线** | 触发沙箱权限拦截、涉及敏感凭证泄露、破坏免审批基线 | 探测受限系统目录、硬编码明文密钥或 Token | 遵守 `rules/security/security_baseline.md` 免审批红线 |

## 📋 三、标准《前置风险评估卡》输出模板

在复杂任务的【筹策】阶段，智能体必须输出如下格式的标准风险卡片：

```markdown
### ⚠️ 前置风险评估与应对预案
- **技术/依赖风险**：[说明底层依赖环境、第三方工具或版本冲突风险；若无则注明“经核验无三方依赖变更”]
- **数据/破坏性风险**：[说明涉及的文件覆盖、状态重置或不可逆重构风险；标明最大影响文件范围]
- **需求边界风险**：[说明当前需求的未决细节或对存量模块的潜在联锁影响]
- **降级与回滚方案**：[明确具体的 Git 回滚命令、备份还原路径或功能降级预案]
```

## 🚨 四、硬性阻断门禁 (Blocker Gates)

若前置风险扫描命中以下**顶级高危条件**，智能体必须**立即暂停执行并阻断流程**，向用户提示确认：
1. **涉及外部线上数据库/生产环境的破坏性变更**（如 Drop/Truncate、清空生产表）；
2. **涉及大规模跨目录文件批量删除或不可逆覆盖**（无版本控制保护的文件批量删除）；
3. **涉及凭证密钥泄露风险或越过免审批安全红线**；
4. **用户原始需求存在互相矛盾的重大模糊定义**（继续执行可能导致完全重做）。
