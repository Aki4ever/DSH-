## 📌 一、版本号格式与标准 (SemVer 规范)

工程全量遵循国际通用的**语义化版本规范 (Semantic Versioning 2.0.0)**，版本号格式统一表达为：

$$\mathbf{v\text{MAJOR}.\text{MINOR}.\text{PATCH}}$$
*示例：`v1.0.0`、`v1.1.0`、`v1.1.1`*

### 1. 三位版本号递增准则
- **主版本号 (MAJOR)**：发生不向下兼容的重大架构重构、核心元规则颠覆、或系统性基础设施大升级时递增（如 `v1.0.0` ➔ `v2.0.0`）；
- **次版本号 (MINOR)**：新增重要业务模块、新增成套领域规范（如新增 Unity 规范、新增完整知识库架构、新增成套需求工单）且向下兼容时递增（如 `v1.0.0` ➔ `v1.1.0`）；
- **修订号 (PATCH)**：局部文字润色、单点规则微调、修复死链、格式整理或微小 bug 修复时递增（如 `v1.1.0` ➔ `v1.1.1`）。

## 🔄 二、三位一体强同步铁律 (Sync Law)

为了彻底杜绝“代码已改但文档脱节”、“需求版本与知识库版本各定各的”这类混乱现象，系统确立强制同步铁律：

```text
┌────────────────────────────────────────────────────────┐
│             工程实际实施版本 (Current Release)           │
│                       v1.1.0                           │
└──────────────┬──────────────────────────┬──────────────┘
               │ 严格同步                  │ 严格同步
┌──────────────▼─────────────┐  ┌─────────▼──────────────┐
│  需求管理台账 (docs/req)    │  │  系统知识库 (knowledge/*)│
│  - 当前总版本: v1.1.0      │  │  - 实施基线: v1.1.0      │
│  - 各条目实施版本映射      │  │  - 各模块对应修订状态    │
└────────────────────────────┘  └────────────────────────┘
```

1. **同批次原子同步**：
   - 任何涉及功能落地、规范制定或代码交付的动作，在任务收尾阶段（【归卷】），必须同时核对并同步更新：
     1. 工程实施版本；
     2. 需求台账（`docs/requirements.md`）中的当前实施总版本号及条目实施版本；
     3. 涉及到的知识库（`knowledge/*`）头部版本元数据区。
2. **禁止版本真空与孤岛**：
   - 不允许存在“没有实施版本号”的需求卡片；
   - 不允许知识库内容领先或落后于实际实施版本，修改内容必同步升版。
3. **受管文档范围与对齐判定（REQ-044 新增，可执行）**：
   - **受管文档**：凡头部含“版本信息与实施追踪”元数据区的文档（`rules/**`、`knowledge/**`、`indexes/**`、`docs/**`、`memory/**`、`templates/**`，以及根级 `AGENTS.md`、`README.md`）；
   - **对齐判定**：受管文档头部“当前文档版本”必须等于台账总版本号；不等即为待对齐项，
     由 `node scripts/legacy_align_scan.mjs --root .` 与 `node scripts/conflict_scan.mjs --root .` 自动列出；
   - **为什么要求"相等"而不是"只许落后"**：各文档自行维护一套版本号会产生大量"版本孤岛"，
     既无法横向比较也无法追责；统一跟随总版本号后，"谁改了什么"由 Git 记录与需求台账回答，职责边界更清楚；
   - **豁免**：模板文件里**示例代码块内**出现的版本号不参与判定（那是示例，不是文档自身的声明）。
