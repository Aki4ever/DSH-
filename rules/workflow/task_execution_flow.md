## 🚦 一、执行双轨分层与判定准则

```text
                       ┌── [难度 ≤ 35分 · 满足捷径条件] ──▶ ⚡ 敏捷捷径通道 (Fast Track)
[输入新任务] ── 意图与打分 ──┤
                       └── [难度 > 35分 · 触碰任一红线] ──▶ 🚨 强制硬约束流 (Hard Line)
```

### 1. 强制必走流程 vs 捷径通道对照矩阵

| 执行环节 | 🚨 强制硬约束流程 (Hard Line) | ⚡ 敏捷捷径通道 (Fast Track) |
| :--- | :--- | :--- |
| **触发门槛** | 难度 $> 35$ 分；或触及跨模块重构、核心规则修改、代码新增、发布升版 | 难度 $\le 35$ 分；纯信息检索、单文件局部微调、文字修正、无害巡检 |
| **1. 会话重命名** | **必须首发调用** `./scripts/rename_session.sh` 锁定 8 字以内标题 | **零豁免硬约束**：同样必须首发调用 `./scripts/name_me.sh` 锁定合规标题 |
| **2. 知识库前置审查** | 强制检索 `knowledge/` 与元规则防冲突，遇冲突立即阻断 | **捷径**：纯技术或格式查询直接作答，重点关注安全底线 |
| **3. 前置风险评估** | **必须显式输出**《前置四维风险评估卡》与回滚预案 | **捷径**：免输出独立大表格，以行内 1 句简述风险与防御 |
| **4. Todo 状态跟踪** | **必须调用** `todo_write` 激活原生 `TodoPanel` 状态条 | **捷径**：单步或简单双步任务免调用 `todo_write` |
| **5. 写后读回校验** | 凡写必读，修改后必须 `read` 读回确认完整性 | 保持一致（修改文件必读回校验，禁止盲目交付） |
| **6. 自动化测试门禁** | **必须编写/运行真实测试脚本**，100% 绿灯方可结项 | **捷径**：纯文档/配置微调，通过终端命令或读回校验即算通过 |
| **7. 页面台账与截图** | 涉及 Web/GUI 变动，强制截图并登记 `Page_*.png` 资产台账 | 非 GUI 前端任务与纯规则任务，完全免除截图与台账 |
| **8. 需求台账与升版** | **三位一体原子同步**：更新 `docs/requirements.md` 并推进版本号 | **捷径**：纯答疑、无实际文件持久化修改的任务免写台账 |
| **9. 收尾复盘与看板** | 强制输出三维 AAR 复盘卡与 M1~M6 效率审计指标看板 | **捷径**：免冗长 AAR 复盘与六维看板，输出精简交付总结与【执行效果】 |

### 2. 流程刚柔分级实施准则 (Rigid vs Flexible Workflow Matrix)

为彻底解决执行边界模糊带来的“过度教条”或“随意跳步”，将系统全生命周期流程严格划分为**绝对刚性实施**与**弹性自适应实施**两大等级：

| 实施等级 | 适用工序与范围 | 执行铁律与边界 | 典型代表 |
| :--- | :--- | :--- | :--- |
| 🔴 **绝对刚性实施**<br>*(Mandatory & Rigid)* | 凡涉及**安全红线、物理真实性、状态判定、可追踪性**的核心底座工序 | **零容忍跳步**：无客观豁免条件，缺一步即判定违规阻断；必须以物理命令退出码 0 或落盘事实为依据。 | 1. 首发改名（`name_me.sh`）<br>2. G0~G4门禁通过性检查<br>3. 写后必读回（Read-Back）<br>4. 物理实证（机器真实输出）<br>5. 规则变更双检（查重+冲突）<br>6. **标准交付输出框架（六大模块，含执行效果）**<br>7. **底层物理锁 Agent 单向工序链（`scripts/physical_lock.sh`）** |
| 🟡 **弹性自适应实施**<br>*(Flexible & Adaptive)* | 涉及**多任务并发调度、深度代码上下文检索、辅助文档落盘、深度复盘卡**等情境化手段 | **按需动态适配**：根据任务难度打分与复杂度自适应裁剪，避免微型任务过度工程化浪费上下文。 | 1. PP-Life 单例并发中枢（单线串行任务豁免并发）<br>2. 深度上下文遍历（单点检索直接收敛）<br>3. 独立 PRD 文件落盘（常规小改行内交代）<br>4. 六维指标全景看板（轻量任务输出精简回溯卡） |

### 3. 底层物理锁 Agent (Physical Lock Agent / PLA) 串行化硬约束

自 `v4.18.0` 起，系统在拦截层与调度底层全域接入**底层物理锁 Agent (PLA)**。
物理锁看守严格单调递增的工序链式状态机（LOCK-0 初始探境 ➔ LOCK-1 定标待筹 ➔ LOCK-2 筹策攻坚 ➔ LOCK-3 质检验证 ➔ LOCK-4 归卷结项）：
- **必须完成上一步，才可以执行下一步**：每一工序阶梯必须向磁盘产生可验证的 Exit Code 0 或状态凭证，未达成时底层拦截器直接对下一工序的改动型工具调用实施物理阻断；
- **全域所有项目强生效**：物理锁机制作为宿主底层基础设施，在所有由 DSH 打开与托管的项目中 100% 强制生效，消灭任何环境例外与流程跳步。

### 4. 需求与五维知识库双轮驱动规范

所有工程任务必须由**需求台账**与**知识库五维法定规范**联合驱动，严禁脱离依据凭空发挥：
- **前置五维规范核对**：根据任务类型，强制贯彻知识库中的**工程规范**（分层/测试/原子性）、**文字规范**（全中文/高可读/报错三段式）、**交互规范**（GenUI 全装配/格式塔）、**美术规范**（主题色/矢量信息图）及**故事背景世界观规范**（设定权威/防冲突）；
- **新项目框架式留白初始化**：新工程初始化立项时，严格贯彻“轻装起步、骨架完备、业务留白”准则，只构建标准骨架与扩展插槽，坚决不填塞假业务代码与伪数据。

## ⚙️ 二、强制硬约束流程：标准六阶十六步流水线

当任务判定为 **Hard Line** 时，依序执行以下十六道工序。**每道工序的强制等级取决于它有没有客观判定手段**：

- 🟢 **强制**：有脚本或明确命令可判定"做了没有、做对没有"，未完成不得推进；判定一律以命令输出为准，不采信口头声明；
- 🟡 **建议**：尚无独立判定手段，按建议执行（做了更好，不做不算违约）；这类工序仍必须避免"只写不做"。

**为什么这样分**：没有判定手段却写成"必须"，等于把约束变成一句口号——既检查不了，也无法追责。
凡后续为某道工序补上了判定脚本，就把该行等级升回 🟢 强制（判定手段列必须填真实存在的路径）。

| 阶段 | 工序号 | 工序名称与核心动作 | 判定手段（🟢 强制 / 🟡 建议） |
| :---: | :---: | :--- | :--- |
| **一、探境** | **S01** | 环境权限与全中文说明自检 | 🟡 建议（按 `AGENTS.md` 红线与语言规范执行） |
| | **S02** | 干道路由与业务基线检索 | 🟡 建议（**判定**：`indexes/shortcuts_index.md` 是否命中） |
| **二、定标** | **S03** | 需求意图提炼与查重 | 🟢 强制（**判定**：`node scripts/redundancy_scan.mjs --root .` 无高相似对） |
| | **S04** | 双螺旋决策打分与轨道判定 | 🟢 强制（**判定**：出分过程必须可见，轨道判定与后续动作一致） |
| | **S05** | 首动任务栏改名闭环门禁 | 🟢 强制（**判定**：`./scripts/rename_session.sh` 执行成功，前端任务栏肉眼可见即时更新，且 `./scripts/check_task_naming.sh --exit` 返回 0） |
| | **S06** | 核心工单与立项赋能确立 | 🟡 建议（新项目立项强制遵循框架式留白初始化准则，以 `templates/project_dsh_bootstrap_template.md` 为准，严禁过度填塞伪代码与假数据） |
| **三、筹策** | **S07** | 任务分解与 Todo 初始化 | 🟢 强制（**判定**：存在 `todo_write` 调用且状态可查） |
| | **S08** | 风险揭示与全局资源防冲突锁定 | 🟢 强制（**判定**：`./scripts/global_scheduler_lock.sh` 申领成功） |
| **四、攻坚** | **S09** | 上下文指纹单次读取 | 🟡 建议（同一文件重复读取不报错但浪费预算） |
| **五、质检** | **S10** | 精准修改与遇碰即对齐 | 🟡 建议（对齐结果由 S13 的存量校准统一判定） |
| | **S11** | 写后强制读回与指纹校验 | 🟢 强制（**判定**：每个被改文件均有对应 `read` 读回记录） |
| | **S12** | 自动化测试与质量门禁 | 🟢 强制（**判定**：测试脚本实跑 100% 绿灯，贴出真实输出） |
| | **S13** | 存量排查与指纹台账同步 | 🟢 强制（**判定**：`node scripts/legacy_align_scan.mjs --root .` 与 `node scripts/conflict_scan.mjs --root .` 清零；`./scripts/fingerprint_audit.sh --scan` 更新完成） |
| **六、归卷** | **S14** | 三位一体版本号强同步 | 🟢 强制（**判定**：台账条目版本与文档头部版本一致） |
| | **S15** | 远程 Git 强同步与释放排他锁 | 🟢 强制（**判定**：`./scripts/git_sync_remote.sh` 推送成功回执） |
| | **S16** | 交付收尾与管控效果审计打分 | 🟢 强制（**判定**：文末包含六大交付模块，且包含 scripts/audit_execution.sh 签发的【执行效果】0~100 分量化打分） |

**结算**：🟢 强制 11 道 · 🟡 建议 5 道（S01 / S02 / S06 / S09 / S10）。
原表述为"十六步全部必须、禁止跳步"，与磁盘上只有 4 项门禁判定的事实不符；
现改为"有判定手段者强制、无判定手段者建议"，并保留升级通道。

## 🛡️ 二之二、任务执行不可跳过的刚性卡点保障机制 (Anti-Bypass Guardrails)

为了根除“口头发誓、随意跳步、盲写盲动、收尾敷衍”的问题，系统确立**“无客观判定不立规，有客观判定必阻断”**铁律。执行任务时该有的流程必须要有，通过以下六大物理防线实施刚性拦截：

| 物理防线 | 卡点工序 | 不可跳过的核心原因 | 自动化机器判定命令 / 工具 | 违规与跳步后果 |
| :---: | :---: | :--- | :--- | :--- |
| **防线 1** | **G0~G4管控门禁** | 确保会话合规命名、工程结构整洁、骨架完备、台账对齐、无重复块 | `./scripts/control_gates.sh check` | `execAllowed=false`，后续写文件动作全面阻断 |
| **防线 2** | **S05 任务栏改名** | 锁定任务分类与难度概述，且必须落实到任务栏，前端肉眼可见成功 | `./scripts/rename_session.sh` RPC 成功 + `./scripts/check_task_naming.sh --exit` | 前端未更新或格式非0，看板警报，动作阻断 |
| **防线 3** | **S07 待办常显** | 任务必须常显在输入框上方，全生命周期可见，杜绝黑盒 | `todo_write` 调用记录（清单非空且包含推进状态） | 上下文切换后失忆；过程无回执，视同盲动 |
| **防线 4** | **S11 写后必读回** | 防止模型幻觉、部分文本替换截断、语法破坏与假落地 | 改动文件必调 `read` 原生工具核验指纹与内容完整性 | 未读回的文件视为“未落地”，禁止进入质检与交付 |
| **防线 5** | **S13 多维双检扫描** | 杜绝碎片化造轮子、杜绝事实自相矛盾与死链残留 | `redundancy_scan.mjs` + `conflict_scan.mjs` + `legacy_align_scan.mjs` | 报错数 > 0 立即阻断合并与推送，要求本轮清零 |
| **防线 6** | **S16 执行效果审计与规范收尾** | 杜绝敷衍交付与虚假达标，由管控审计智能体给出 0~100 分量化评分 | `./scripts/audit_execution.sh --exit`（分数 ≥ 85 且包含六大要素） | 低于 85 分或格式要素残缺直接触发质量驳回，禁止结项 |

## 🔄 二之三、任务执行全景闭环流水线（八阶端到端细致流线）

全域任务执行必须完整走完从意图到收尾的八阶闭环流水线。每个阶段均定义了明确的输入前置条件、核心动作、客观判定命令与产出物标准：

```text
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 阶段0：意图接收 │ ──▶ │ 阶段1：探境自检 │ ──▶ │ 阶段2：定标分流 │ ──▶ │ 阶段3：筹策建单 │
└─────────────────┘     └─────────────────┘     └─────────────────┘     └─────────────────┘
                                                                                 │
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐              ▼
│ 阶段7：交付收尾 │ ◀── │ 阶段6：归卷同步 │ ◀── │ 阶段5：严苛质检 │ ◀── ┌─────────────────┐
└─────────────────┘     └─────────────────┘     └─────────────────┘     │ 阶段4：攻坚落地 │
                                                                        └─────────────────┘
```

### 阶段 0：意图接收与边界锁定 (Intent Ingestion)
- **输入前置**：接收用户的直接指令或上下文提问；
- **核心动作**：
  1. 剥离非核心修饰词，提炼核心任务诉求与验收标准；
  2. 划定本次任务的影响边界（受管规则、业务代码、配置脚本或文档台账）。
- **客观判定**：明确本次产出形式是“仅方案规划”还是“真实落地实施”。
- **阶段产出**：结构化意图定义与验收判据。

### 阶段 1：探境自检与准入复核 (Preflight Inspection)
- **输入前置**：任务意图确立；
- **核心动作**（严格顺序，严禁跳步）：
  1. **查红线**：读 `rules/security/security_baseline.md`，确立数据与权限安全底线；
  2. **看元规**：读 `rules/system/meta_rules.md`，落实最高优先级规则约束；
  3. **走干道**：检索 `indexes/shortcuts_index.md`，优先复用已注册的高速通道；
  4. **核知识库**：检阅 `knowledge/` 对应项目，执行前置防冲突核查；
  5. **查台账**：核查 `docs/requirements.md`，确认基线版本与当前实施进度；
  6. **读记忆**：检阅 `memory/` 历史避坑沉淀与用户偏好；
  7. **门禁复核**：执行 `./scripts/control_gates.sh check` 确认系统底座健康度。
- **客观判定**：`./scripts/control_gates.sh check` 输出 4/4 通过且 `execAllowed=true`。
- **阶段产出**：前置基线与安全上下文环境加载就绪。

### 阶段 2：定标、双螺旋打分与会话改名 (Scoring & Naming S01~S06)
- **输入前置**：前置探境无阻断；
- **核心动作**：
  1. **查重对比**：比对历史需求台账，避免同质化重复造轮子；
  2. **双螺旋打分**：按影响范围(30) + 依赖深度(30) + 安全风险(20) + 复杂度(20) 精确出分；
  3. **轨道分流**：$\le 35$ 分进入 Fast Track；$> 35$ 分或触及核心底座锁定 Hard Line；
  4. **首动改名握手**：通过改名脚本锁定标题格式 `[分类编号][难度分] 8字概述`。
- **客观判定**：`./scripts/check_task_naming.sh --exit` 退出码为 0，看板常显合规提示。
- **阶段产出**：会话标题锁定与既定执行轨道。

### 阶段 3：筹策拆解与可视化待办挂载 (Planning & Tracking S07~S08)
- **输入前置**：执行轨道确定；
- **核心动作**：
  1. **挂载待办条**：调用 `todo_write` 写入多步任务步骤，任何执行时刻至少 1 项为 `in_progress`；

- **客观判定**：输入框上方原生 `TodoPanel` 状态非空，工具回执具备真实步骤。

### 阶段 4：攻坚落地、精准修改与写后必读回 (Execution & Read-Back S09~S11)

  1. **上下文精准读取**：通过 `read` 或 `grep` 定位目标区域，严禁盲改；

  3. **写后强制读回**：每一次物理写入完成后，**必须立即调用 `read` 读回修改后文件**，核验格式、语法与完整性。

## 🏛️ 二之四、任务执行四级解耦体系：索引 ➔ 路由 ➔ 接口 ➔ 执行 (REQ-067)

本体系确立了任务执行的全链路标准化解耦机制，杜绝“隐形能力”“无序穿透”与“黑盒不透明”：

```text
┌──────────────────────────────────────────────────────────────┐
│ 1. 索引层 (Index)     权威能力字典，提供 Identifier 与正反案例 │
└──────────────┬───────────────────────────────────────────────┘
               ▼
┌──────────────────────────────────────────────────────────────┐
│ 2. 路由层 (Route)     意图导航器，规划途径站、前置门禁与目标接口│
└──────────────┬───────────────────────────────────────────────┘
               ▼
┌──────────────────────────────────────────────────────────────┐
│ 3. 接口层 (Interface) 开放契约窗口，声明入参/出参/边界/降级预案 │
└──────────────┬───────────────────────────────────────────────┘
               ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. 执行层 (Execution) 原子作业引擎，内部黑盒封装，返回标准回执  │
└──────────────────────────────────────────────────────────────┘
```

### 1. 四级分工与核心铁律
1. **索引层 (Index Layer)**：
   - 权威载体：[`indexes/capabilities_index.md`](../../indexes/capabilities_index.md)；
   - 铁律：系统内所有可用脚本、工具、技能、协议必须注册唯一点分标识（Identifier）与正反案例，不登记一律视为“不存在的能力”。
2. **路由层 (Routing Layer)**：
   - 权威载体：[`indexes/navigation_router.md`](../../indexes/navigation_router.md) 与 [`scripts/route_navigate.mjs`](../../scripts/route_navigate.mjs)；
   - 铁律：根据用户输入意图，规划“起点 ➔ 权限环境 ➔ 门禁判定 ➔ 目标接口 ➔ 避坑路况”五段式地图导航卡片，完成意图至标准接口的精准派发。
3. **接口层 (Interface Layer)**：
   - 权威载体：[`indexes/tool_interfaces.md`](../../indexes/tool_interfaces.md)；
   - 铁律：所有执行层能力必须开放标准契约（声明适用边界、输入参数 Schema、结构化输出、容错降级与安全级别），对调用方暴露统一门面。
4. **执行层 (Execution Layer)**：
   - 权威载体：`scripts/*`、`ai-control/*`、Cordis 插件等具体作业单元；
   - 铁律：高内聚黑盒封装，具体实现细节对外部调用方透明。一旦路由层确定调用，直接走接口层声明的方法，执行层独立闭环并返回确定性结果（标准退出码 + JSON/Markdown 回执）。

### 2. 任务全生命周期动态更名与全局调度句柄治理 (Task Name as Dispatch Handle)
- **首动命名门禁**：任何任务启动，必须首先在 S05 工序对齐会话命名（格式：`[分类编号][难度分] 8字概述`），严禁未命名或纯代号执行；
- **任务名即调度句柄**：改名成功后的标准化三要素标题，自动成为该任务在生命周期中的**全局唯一业务调度句柄 (Task Dispatch Handle)**。后序所有跨智能体分发（Agent PP ➔ Agent Life）、全局资源锁申领、阶段原子回执与审计台账登记，必须显式携带该任务名作为精准指代锚点，杜绝调度混淆与串台；
- **阶段演进动态更名**：在执行生命周期中，当任务从前期分析流转至核心攻坚、集成测试或收敛交付时，必须随阶段演进触发动态更名；
- **前端实时穿透**：所有更名动作必须执行 `./scripts/rename_session.sh`，通过 DSH 宿主 RPC 广播原地穿透至前端任务栏与侧边栏，实现前端看板肉眼可见即时更新，杜绝前后端信息脱节；
- **机器判定守护**：由 `scripts/check_task_naming.sh` 与 `scripts/batch_rename_sessions.mjs` 实施全自动化探测与自愈。

### 3. 任务级版本-需求联动与前端同步规约
- **前置需求绑定与生成**：执行任何任务前，必须前置匹配既有需求（增量演进）或生成对应的新需求编号（`REQ-xxx`），明确验收标准；
- **语义化版本联动递增**：按照 SemVer 规范，代码与文件变动必须伴随语义化版本号刚性递增，并在前端状态栏/版本徽标中同步呈现最新版本号与当前关联需求 ID，杜绝无版本裸跑；
- **版本对齐即时校验**：通过 `./scripts/control_gates.sh check` 实时校验版本与需求同步状态。

### 4. 执行收敛态需求落盘与“以需定测”闭环规约
- **收敛态即时回写落盘**：任务执行进入收敛阶段时，产生的所有技术决策、架构变动、配置改动必须第一时间同步写回项目文件夹内的需求文件（`docs/requirements.md` 等），禁止仅停留在会话上下文中；
- **“以需定测”闭环验证**：测试环节必须严格以需求文件中列明的“验收标准 (Acceptance Criteria)”作为唯一基准进行执行与测试，所有测试结果必须逐项对齐需求条款；凡未经测试验证的项必须明文声明“未验证”，方可进入收敛交付；
- **“项目初始化”快速通道支撑**：确立“项目初始化”为 G0/G1 快速通道关键词，秒级调用 `scripts/init_project.sh` 自动生成项目结构、骨架防丢文件并做好 `v1.0.0` 基础版本基线，供后续快速调用与迭代。

### 5. 执行驱动四级解耦自底向上逆向强同步规约 (Bottom-Up Capability Sync Protocol)
- **底层驱动上层同步**：索引层和路由层必须根据执行层的能力更新来同步更新。凡是执行层（`scripts/*`、`ai-control/*`、插件工具）新增脚本、修改命令参数或下线旧能力时，绝对禁止“仅写脚本、上层装作不知道”的暗黑能力行为；
- **三层逆向冒泡强同步**：在同一原子任务生命周期内，必须完成自底向上的四级联动：
  1. **接口层 (`tool_interfaces.md`)**：登记/更新能力入参 Schema、退出码与降级容错方案；
  2. **路由层 (`shortcuts_index.md` / `navigation_router.md`)**：增补或对齐自然语言快速触发词通道，更新地图导航路径；
  3. **索引层 (`capabilities_index.md`)**：上架/刷新能力唯一标识符（Identifier），并补齐正面使用范例与反面踩坑红线；
- **机器拦截硬门禁**：改动后必须运行 `node scripts/channel_audit.mjs`，通道冲突或死链未归零前，门禁系统判定为不合格，禁止关闭任务。

## 📌 三之一、任务常显在输入框（可视化任务条）

**要求**：任务无论**完成与否**，都必须常显在输入框上方，用户不必往回翻记录就知道"在做什么、还剩什么"。

### 1. 挂载在哪（DSH 原生，无需自研组件）

| 常显组件 | 挂载槽位 | 展示内容 | 由什么驱动 |
| :--- | :--- | :--- | :--- |
| **`TodoPanel`** 任务待办条 | `conversation.input.dock`（order=0） | 实时清单：已完成 N · 进行中 N · 待办 N，默认折叠为一行，可展开 | `todo_write` 写入的清单 |
| **`GoalBar`** 目标条 | `conversation.input.dock`（order=10） | 长期目标文本与轮次进度（含 Edit/Pause/Resume/Clear） | `create_goal` / `update_goal` |

### 2. 唯一失效条件（源码级判定依据）

`TodoPanel` 的实现里有一条硬判定：`if (todos.length === 0) return null;`
（依据：`@deepseek-ai/dsh-client-ui-conversation` 客户端渲染代码）。

因此结论很明确：

- **清单非空 → 常显**，完成态照样常显（完成项显示为勾选态，标题栏计数仍列出"已完成 N"）；
- **清单为空 → 消失**，这才是"输入框上方空了"的唯一原因；
- 补充事实：`todo_write` 的 `content` 必须是非空字符串（依据：`@deepseek-ai/dsh-tool-todo` 校验），
  所以清单**只会被整表替换、不会被清空** —— 只要写入过，就一直在。

### 3. 执行规范（三条硬要求）

1. **开工即建清单**：标准完备流任务在动手前必须 `todo_write`，至少含 3 项，且**任何时刻至少一项为 `in_progress`**；
2. **收尾不清空**：任务结束时保留**全部完成态**的清单（标 completed 即可），**严禁**用空数组或删除动作清掉清单；
3. **长任务建目标条**：预计跨多轮、需要自主续跑或按轮次推进的任务，必须 `create_goal`，使 `GoalBar` 常显目标与轮次。

### 4. 判定手段（可执行）

| 判定什么 | 怎么做 | 通过标准 |
| :--- | :--- | :--- |
| 清单是否存在且实时 | 自查最近一次 `todo_write` 调用的内容（工具回执即证据） | 清单非空，且状态与本轮真实进展一致 |
| 目标条是否存在 | `get_goal` | 长任务返回 `phase=active` 的目标与轮次 |
| 输入框上方为空时如何归因 | 若清单为空 → 属"未建清单/被清空"违规，立即补建；若清单非空仍看不到 → 属前端渲染问题，按宿主问题上报，不要反复写清单 | 归因明确，不猜 |

> **一句话记忆**：清单在，进度就在；清单空，进度就没了。所以"不清空清单"不是洁癖，是常显的前提。

## ⚡ 四、敏捷捷径通道：极简三步流

当任务判定为 **Fast Track** 时，执行极简三步闭环：
1. **【探】(快速感知)**：通过 `read` 或 `grep` 定位目标，激活 ReadCard，行内确认无高危风险；
2. **【攻】(精准落地)**：通过 `edit` 激活 DiffCard 进行最小粒度修改，紧随 `read` 读回确认；
3. **【归】(精炼交付)**：输出结构化交付说明与可点击链接，跳过冗长看板，快速响应。

## 🏷️ 五、任务打分与命名

### 1. 难度打分与轨道联动

$$\text{难度总分} = \text{影响范围}(0\sim30) + \text{依赖深度}(0\sim30) + \text{安全风险}(0\sim20) + \text{技术复杂度}(0\sim20)$$

- **[35~100分]**：自动进入 **Hard Line** 强制完备流；
- **[0~34分]**：自动进入 **Fast Track** 敏捷捷径通道。

### 2. 会话命名格式与自动命名

命名格式（三要素构成、逐条硬性规则、正反示例、字数口径）**唯一权威源**：
[`knowledge/common/task_naming_spec.md`](../../knowledge/common/task_naming_spec.md)。

**执行时机（本节职权）**：定标打分完成后、任何实质动作之前，首发调用
[`scripts/rename_session.sh`](../../scripts/rename_session.sh) 按上述规范锁定标题（对应 §二 的 S05 首动握手门禁）。

## 🛡️ 六、交付收尾刚性规范：文末固定总结结构与全域管控执行 (Mandatory Tail Delivery & Global Guardrail)

### 1. 文末固定五联装总结结构 (全域绝对刚性实施项 · 视觉强化规范)
为了彻底杜绝冗长信息过载与无效堆砌，每次任务执行、阶段汇报或对话答复的**最后一行输出区域**，必须留出标准化、精简的固定总结结构。该结构**必须且仅包含以下五个标准字段**，顺序固定，严禁随意删除或缺漏，且必须使用**加粗与显式视觉图标强化**：

```markdown
---

### 📦 任务执行与交付收尾回执

- **🏷️ 【当前状态】**：明确标注处于【规划阶段】还是【实施阶段】
- **🎯 【核心结论/输出物】**：有输出物就给具体输出物说明，没有输出物就给核心结论
- **📍 【输出物地址】**：如果有输出物就要给物理文件路径（行内代码格式），没有输出物填「无」
- **💡 【重要说明】**：对执行过程中遇到的问题、踩坑、潜伏风险或连带产生的非预期/连带改动进行透明显式说明
- **🌟 【执行效果】**：必须给出 0~100 分量化审计打分及扣分项，方便审计和回溯总结
```

### 2. 五要素字段填写规范与铁律
1. **🏷️ 【当前状态】**：首字必须明确二选一状态（【规划阶段】或【实施阶段】）；纯分析/未改动文件严禁冒充实施态，实际修改落盘并校验后方可声明为实施阶段；
2. **🎯 【核心结论/输出物】**：有实体产物时直接明确产物名称与形态（代码/补丁/文档/脚本）；无产物时一针见血给出最终定性或决策核心结论；
3. **📍 【输出物地址】**：存在实体产物时，必须格式化为 Markdown 行内代码（如 `` `rules/...` ``、`` `scripts/...` ``）呈现物理文件相对路径或真实访问链接；无产物时统一填写「无」；
4. **💡 【重要说明】**：高度精炼透明。必须如实披露执行过程中解决的隐藏问题、代码合并中的连带改动、环境边界或用户可能未察觉的深层系统影响；若完全无附带改动则填写「按期依规交付，无额外非预期改动」；
5. **🌟 【执行效果】**：必须给出 0~100 分量化审计打分卡片或客观得分数值，包含扣分明细与履约依据，供追溯审计，严禁口头虚标。

### 3. 全域工程管控五大核心律 (Global Guardrail Five Laws)
1. **执行必入台账与消重冲突处理**：所有代码/规则执行必须前置转化为需求条目（REQ-xxx）；写前必跑冗余与冲突扫描，重复归并，冲突先裁决后入库；
2. **需求版本强递增与依据最新版本执行**：需求变动必须同步递增版本号；所有执行工序必须以最新版本需求文档为唯一标准；
3. **需求映射测试用例与全绿门禁**：测试用例必须 100% 逐条覆盖需求验收项；交付前必须跑通自动化测试，零失败方可结项交付；
4. **知识库规范绝对最高法定基线**：知识库（`knowledge/`）为最高法定基线；业务需求与知识库冲突时，无条件以知识库规范纠偏需求；
5. **存量工程全域批量规范化**：管控升级必须对全域所有 DSH 工程文件夹生效，自动化执行存量工程检测与批量规范化对齐。

### 4. 极简精准输出铁律 (Strict Relevance & Frugality)
答复内容严守最小输出原则：**与任务不相关的少说，没有问到的不要说，只有很相关并且比较重要的才说**。坚决剔除无关寒暄、冗余铺垫与过程流水账，确保高信噪比。

## 🛡️ 七、执行安全与防死循环铁律

1. **两步无进展熔断 (Circuit Breaker)**：若同一错误连续尝试两次无增量，必须立即阻断并报错，禁止盲目反复重试；
2. **绝对白名单保护**：执行任何清理或批量修改时，`knowledge/`、`memory/`、`rules/`、`indexes/`、`docs/` 核心资产绝对禁止删除；
3. **GFM 原生组件规范**：禁止输出裸 HTML 标签，一律使用标准 Markdown 引用块（`>`）与表格呈现视觉卡片；
4. **报错归因与防复发闭环 (Error Ledger Sync)**：遇到工具调用报错，严禁静默吞没或无归因盲试，必须在思维链中执行三段式解构（中文释义+物理根因+修复路径），并将具复发特征的共性错误登记至 [`memory/error_ledger.md`](../../memory/error_ledger.md)，反哺前置自检探针。
5. **每动必升版与输出物强同步 (Per-Task Version Bump & Deliverable Sync)**：每次实质物理变更任务，必须将系统实施总版本号显式递增；产出的实体交付物（文档头部元数据、代码注释、图形快照）与需求管理主台账 [`docs/requirements.md`](../../docs/requirements.md) 必须 100% 同步更新最新版本号，绝不允许版本悬空或交付物旧版残留。
