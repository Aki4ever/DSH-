# 任务执行结构化流程与图形化交互规范 (Task Execution Flow & Visual Standards)

本文档规范了智能体在处理日常研发、规则治理与维护任务时的**结构化执行流程**、**统一任务命名与量化打分模型**，以及**全套可复用的图形化交互组件标准**。

---

## 🧭 一、核心理念与标准六步管道

任何任务的落地，均需经过严密的工程化闭环。我们将任务全生命周期提炼为“六步闭环”：

```text
[用户任务] ──▶ 1. 探境 ──▶ 2. 定标 ──▶ 3. 筹策 ──▶ 4. 攻坚 ──▶ 5. 质检 ──▶ 6. 归卷 ──▶ [交付成果]
              (探知环境)     (明确边界)     (规划方案)     (实施改造)     (核验证明)     (台账闭环)
```

---

## ⚡ 二、流程速查与操作指代命名矩阵

用户在与智能体交互时，可直接使用**双字代号**、**单字代号**或**快捷指令**指示特定环节：

| 阶段序号 | 官方标准全称 | 双字代号 (口语推荐) | 单字代号 | 快捷指令 (斜杠/标签) | 阶段核心价值与动作 |
| :---: | :--- | :---: | :---: | :---: | :--- |
| **01** | **环境探知与上下文扫描** | **探境** | **探** | `/detect` 或 `[探境]` | 扫描工作区目录、运行沙箱、Git 分支与相关文件现状 |
| **02** | **意图提炼与边界定标** | **定标** | **定** | `/scope` 或 `[定标]` | 提炼本质诉求，查重去重，确定交付标准与不做的边界 |
| **03** | **方案推演与步骤筹策** | **筹策** | **筹** | `/plan` 或 `[筹策]` | 拆解技术方案与依赖拓扑，建立 `todo` 分步实施清单 |
| **04** | **精准实施与原子攻坚** | **攻坚** | **攻** | `/exec` 或 `[攻坚]` | 恪守先读后改，最小影响面编写/修改代码、配置与文档 |
| **05** | **多维核验与联动质检** | **质检** | **验** | `/verify` 或 `[质检]` | 语法检查、运行验证、存量规则与文档的联动排查 |
| **06** | **成果交付与闭环归卷** | **归卷** | **归** | `/close` 或 `[归卷]` | 给出结构化交付汇报，双向同步需求台账并提交 Git |

## 📊 三、任务栏统一命名规范与四维量化打分模型

### 1. 统一命名协议
所有正式工程任务必须在任务栏、状态汇报与台账中使用统一格式命名：
$$\text{任务命名} = \mathbf{[任务编号][难度等级·分值/分级名称]\ 任务概述}$$
- **标准示例**：`[TASK-011][P2·5分/中等] 落地图形化进度标记与起止仪式规范`

### 2. 四维难度量化打分模型 (1 ~ 10 分)
杜绝主观拍脑袋定级，通过以下四个可客观度量的维度加权评分：
$$\text{总得分} = \text{影响范围}(1\sim3) + \text{依赖深度}(1\sim3) + \text{风险等级}(1\sim2) + \text{实现复杂度}(1\sim2)$$

| 评估维度 | 分值 | 评定基准与典型场景 |
| :--- | :---: | :--- |
| **影响范围 (Scope)** | **1**<br>**2**<br>**3** | 单文件微调、注释修改、局部格式润色<br>涉及单目录下的多文件或单功能模块整体改造<br>全局性架构调整、跨目录核心链路改动、元规则调整 |
| **依赖深度 (Dependency)** | **1**<br>**2**<br>**3** | 无外部依赖，自包含独立单元<br>与同级规则/模块存在上下游依赖，需跨文件联动核验<br>涉及底层运行环境、基座配置、第三方生态强绑定 |
| **风险等级 (Risk)** | **1**<br>**2** | 低风险，改动可即时安全回滚且无破坏性副作用<br>高风险，涉及不可逆文件清除、生产配置破坏或系统安全红线 |
| **实现复杂度 (Complexity)** | **1**<br>**2** | 纯文本、说明文档、结构化模板配置<br>涉及动态逻辑、算法演进、多层状态机或复杂的编排脚本 |

### 3. 分级映射速查表

| 难度等级 | 分值区间 | 分级名称 | 对应任务特征 |
| :---: | :---: | :---: | :--- |
| **P0** | **8.0 ~ 10.0 分** | **极高难 / 致命级** | 系统核心元规则重构、破坏性架构清理、灾难级紧急修复 |
| **P1** | **6.0 ~ 7.5 分** | **高难 / 复杂级** | 跨模块多系统联动治理、复杂业务重构、多 agent 编排系统 |
| **P2** | **3.5 ~ 5.5 分** | **中等 / 标准级** | 新增独立规范/规则、标准业务模块开发、典型功能迭代 |
| **P3** | **1.0 ~ 3.0 分** | **轻量 / 简单级** | 局部文案修改、单点文件补丁、无害化信息查询与体检 |

## 🎨 四、统一可复用图形化组件标准原型

### 1. 统一图形化任务启动卡片 (Task Start Card)
任务正式开启时，第一条输出强制渲染此卡片：

```text
╔══════════════════════════════════════════════════════════════════════════════════╗
║ 🚀 任务正式启动 ｜ TASK INITIATED                                              ║
╠══════════════════════════════════════════════════════════════════════════════════╣
║ 📌 任务命名：[TASK-xxx][等级·分值/分级] 任务概述                                 ║
║ 📊 难度量化：X.X 分 [范围:x + 依赖:x + 风险:x + 复杂:x] ➔ Px-等级                ║
║ 🧭 六步管道：[1.探] ➔ [2.定] ➔ [3.筹] ➔ [4.攻] ➔ [5.验] ➔ [6.归]                 ║
║ 🎯 核心目标：明确本次任务达成的核心可量化结果                                    ║
╚══════════════════════════════════════════════════════════════════════════════════╝
```

### 2. 双层全图形化进度常显标记 (Dual Graphical Progress Bar)
在每个阶段流转或关键汇报信息顶部常显，包含全局长条与当前子步状态节点：

```text
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 🌐 全局总进度：[████████████████░░░░░░░░] 66%  [阶段 4/6：攻坚]                  │
│ 📍 攻坚子进度：[● 已读原码] ──▶ [● 正在写入] ──▶ [○ 待更新关联] (2/3 步)        │
└──────────────────────────────────────────────────────────────────────────────────┘
```

- **第一层（全局进度）**：采用 24 格高兼容 Unicode 进度方块 `[████░░░░]`，实时显示完成百分比与当前大阶段；
- **第二层（局部子步）**：采用有向拓扑节点 `[● 已完成] ──▶ [○ 待执行]`，精确展示当前阶段内部微步推进。

### 3. 统一图形化任务完成卡片 (Task Finish Card)
任务圆满达成时，最后一条输出强制渲染此卡片收尾：

```text
╔══════════════════════════════════════════════════════════════════════════════════╗
║ 🏁 任务圆满完成 ｜ TASK COMPLETED                                               ║
╠══════════════════════════════════════════════════════════════════════════════════╣
║ 📌 任务命名：[TASK-xxx][等级·分值/分级] 任务概述                                 ║
║ 🌐 全局总进度：[████████████████████████] 100% (6/6 阶段全达成)                 ║
║ 📦 落地交付清单：                                                                ║
│   ├── 文件路径 1 (更新说明)                                                      │
│   └── 文件路径 2 (更新说明)                                                      │
║ 🛡️ 质检排查：语法校验通过、存量联动无破坏、链接与规范有效                        ║
║ 🔄 闭环归卷：需求台账双向回写完成，Git 语义化提交已推送到远程                    ║
╚══════════════════════════════════════════════════════════════════════════════════╝
```

## 🔍 五、各阶段执行细则

### 阶段 1：【探境】(Environment Sensing)
- **定位**：行动前全面摸底，严禁盲目行动。
- **标准动作**：
  1. 使用文件发现工具（`glob`）探测当前目录树与相关文件路径；
  2. 感知环境上下文（沙箱模式、免审批策略、Git 分支状态）；
  3. 读取与任务相关的核心配置文件或既有规范。
- **交付产物**：工程现状基线、涉及文件列表。

### 阶段 2：【定标】(Requirement Scoping)
- **定位**：拒绝模糊歧义，建立确定性契约。
- **标准动作**：
  1. 剥离口语修饰，提炼明确的输入、处理逻辑与输出标准；
  2. 检索 [`docs/requirements.md`](../../docs/requirements.md) 查重核验，判断是全新、优化还是重复；
  3. 执行难度四维打分，并在台账中建卡登记。
- **交付产物**：结构化需求工单、量化分值、预期交付标准。

### 阶段 3：【筹策】(Solution Planning)
- **定位**：先思后行，杜绝边写边改的返工。
- **标准动作**：
  1. 制定分步实施策略与依赖拓扑；
  2. 使用任务追踪工具（`todo_write`）初始化任务清单；
  3. 预判潜在破坏性风险并制定兜底措施。
- **交付产物**：清晰的实施蓝图、拆解后的待办任务清单。

### 阶段 4：【攻坚】(Atomic Execution)
- **定位**：工程落地的关键实操阶段。
- **标准动作**：
  1. **铁律**：改动已有文件必须先读后改（Read before Edit/Write）；
  2. 精准调用文件工具与环境命令，按规划顺序逐步实施；
  3. 实时推进任务状态，杜绝批量或虚假报完。
- **交付产物**：已落地的源代码、配置文件或规则文档。

### 阶段 5：【质检】(Quality Verification)
- **定位**：交付前最后一道防线与存量联动体检。
- **标准动作**：
  1. 执行测试、语法检查与构建脚本；
  2. 依据 [`rules/workflow/audit_and_cleanup.md`](audit_and_cleanup.md) 触发存量联动排查；
  3. 核查文档语言是否平实通俗、无生僻字，链接是否有效。
- **交付产物**：校验测试报告、存量联动排查结果。

### 阶段 6：【归卷】(Archiving & Closing)
- **定位**：干净收尾，沉淀台账与版本轨迹。
- **标准动作**：
  1. 回写需求管理台账（`docs/requirements.md`），更新条目状态；
  2. 将所有待办项置为 `completed`；
  3. 执行 Git 语义化提交（feat / update / deprecate）并推送到远程；
  4. 渲染统一图形化任务完成卡片。
- **交付产物**：交付验收卡片、台账更新、Git 提交记录。

## 🎛️ 六、日常敏捷操作模式（调度套路）

用户可根据任务规模自由组合流程代号：

1. **全通交付流（探 ➔ 定 ➔ 筹 ➔ 攻 ➔ 验 ➔ 归）**：
   - 适用于：中大型复杂任务、全新功能实现、重要规则建立。
   - 口令：`按全流程执行：<任务描述>`。
2. **轻量快修流（定 ➔ 攻 ➔ 验）**：
   - 适用于：边界明确的小型 Bug 修复、文案微调、小范围配置修改。
   - 口令：`跳过探境，直接定标+攻坚：<任务描述>`。
3. **方案推演流（探 ➔ 定 ➔ 筹）**：
   - 适用于：重构前的可行性评估、技术路线预研，只出方案不改代码。
   - 口令：`只执行到筹策，先不要攻坚`。
4. **存量体检流（探 ➔ 验 ➔ 归）**：
   - 适用于：系统健康检查、废旧文件清理、孤岛规则排查。
   - 口令：`对 rules 目录执行体检与质检，排查存量冲突`。

## 📝 七、利于智能体执行的标准工单模板

用户在派发任务时，可直接采用如下模版下发，触发最高保真度的自动化执行：

```markdown
# 【任务执行工单】
- 目标：<简述本次要达成的核心目标>
- 调度模式：<全流程 / 仅筹策 / 攻坚+质检 等>
- 约束要求：
  1. 严格遵守《任务执行结构化流程与图形化交互规范》；
  2. 输出标准图形化启动卡片、双层图形进度条与完成卡片；
  3. 任务标题遵循 [TASK-xxx][难度等级·分值/分级] 格式；
  4. 完成后在 docs/requirements.md 登记闭环并提交 Git。
```
