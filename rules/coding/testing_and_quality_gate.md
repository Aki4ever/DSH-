# 自动化测试与工程质量门禁规范 (Automated Testing & Quality Gate Specification)

> ### 🏷️ **版本信息与实施追踪**
> - **当前文档版本**：`v3.9.0`
> - **对应实施版本**：`v3.9.0`
> - **最后更新日期**：2026-09-16
> - **版本状态**：`[Release 生效]`

本文档制定了工程研发与任务交付中必须严格遵守的**自动化测试与质量验收门禁规范**。代码未测非可信，绿灯方可言交付，杜绝假设性通过与带病交付。

---

## 🧭 一、核心原则与硬性铁律

### 1. 核心铁律
1. **需求即断言 (Requirements as Assertions)**：需求中的每一项功能点与边界异常点，都必须能够映射为明确、可自动运行的断言条件；
2. **命令真实跑通 (Real Execution)**：测试用例必须通过终端工具在环境内真实执行并收集输出，严禁在思考中假设“这应该没问题”；
3. **100% 绿灯交付门禁 (Zero-Failure Gate)**：自动化测试通过率必须为 100%。任何一个用例失败，均视为交付不合格，严禁提交代码或向用户汇报交付。

---

## 🧪 二、分层测试覆盖标准

根据工程任务性质，智能体必须构建对应层级的自动化测试覆盖：

```text
┌────────────────────────────────────────────────────────┐
│             端到端 / 业务场景自动化验收测试              │
│       (E2E / CLI Runner / 业务流程用例 100% 通过)        │
├────────────────────────────────────────────────────────┤
│                 核心模块集成与接口测试                  │
│       (API / 组件状态联动 / 边界异常与降级断言)            │
├────────────────────────────────────────────────────────┤
│              基础单元测试与静态结构校验                 │
│       (Unit Tests / 语法校验 / 类型检查 / 规则链接合规)   │
└────────────────────────────────────────────────────────┘
```

| 工程类型 | 测试执行手段 | 核心断言内容 | 门禁通过指标 |
| :--- | :--- | :--- | :--- |
| **Web 前端工程** | Jest / Vitest / Playwright / pnpm test | 组件渲染、交互事件响应、路由切换、API Mock 状态 | Tests: 100% pass, 0 failed |
| **Python / 后端工程** | pytest / unittest / 脚本自检 | 函数输出断言、异常捕获、数据格式校验 | 100% passed, exit code 0 |
| **Unity 游戏工程** | Unity Test Runner / 编辑器批处理验证 | 场景加载、预制体依赖完整性、无 Missing 引用、无 NullReference | 编译无 Error，用例全绿 |
| **规则/文档/架构工程** | 专用自检测试脚本 (Shell / Node / Python) | 规则文件存在性、Markdown 链接有效性、版本号强同步一致性 | 验证脚本返回 exit code 0 |

## 🚪 三、质量门禁 (Quality Gate) 拦截与执行闭环

在进入任务【五、质检】（S12）与【六、归卷】前，质量门禁自动启动：

```text
[编写功能代码] ──▶ [编写/更新测试用例] ──▶ [真实执行自动化测试]
                                                │
                ┌─── [测试未通过 / 断言报错] ────┴──── [测试全部通过 (100%)] ───┐
                ▼                                                              ▼
        【立即阻断归卷】                                               【准入归卷阶段】
     定位根因并原地修复                                              输出测试证据回执
                │                                                              │
                └────────────────── 重跑测试 ──────────────────────────────────┘
```

### 1. 拦截阻断机制
- 若测试出现哪怕 1 个 Failure / Error，立即阻断工序流转，禁止进入需求台账回写与 Git 提交；
- 智能体必须输出失败分析卡，定位根因后原地重构修复，直至重跑测试全绿。

### 2. 交付证据标准
在向用户交付或总结时，必须以标准代码块形式给出真实的测试运行回执，包含：
- 测试执行命令；
- 执行用例总数 (Passed / Total)；
- 耗时与最终状态标记。
