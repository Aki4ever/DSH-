## ⚛️ 一、原子性核心定义与工程哲学

**原子性 (Atomicity)** 指一个操作或业务流程是**不可分割的最小执行单元**：
- **全成或全败 (All-or-Nothing)**：流程中的所有子步骤要么全部成功生效；只要有任何一步失败，必须全量自动撤销并恢复至初始状态；
- **零中间态暴露**：在操作执行过程中，外部无法观察或读取到处于“半完成”状态的脏数据；
- **不留孤岛与垃圾**：彻底根除孤立文件、脱节版本、损坏存档与不一致台账。

## 🛠️ 二、必须做成原子性的【操作级清单】(Operational Atomicity)

在智能体日常执行、代码重构与 Git 版本管理中，以下操作必须遵循严格的原子性：

### 1. 规则与需求双向同步操作
- **边界定义**：需求登记（`docs/requirements.md`）➔ 规则编写（`rules/*`）➔ 索引更新（`indexes/*`）➔ Git 提交。
- **原子约束**：严禁“只写了规则文件却没登记需求”，或“只更新了需求却没落地规则”。这四步必须在同一任务生命周期内原子闭环提交。

### 2. 新建目录四件套初始化操作
- **边界定义**：创建物理目录 ➔ 创建 `.gitkeep` ➔ 创建 `README.md` 专属说明 ➔ 在父级或全局总索引登记。
- **原子约束**：严禁创建只有目录名字的空壳文件夹。调用 `./scripts/init_dir.sh` 时必须一次性完成四件套，缺一不可。

### 3. Unity 资产文件与伴生 `.meta` 的操作
- **边界定义**：资产文件（如 `Texture.png`）的移动、重命名、删除操作 与 其伴生 `.meta` 文件（`Texture.png.meta`）的对应操作。
- **原子约束**：必须成对同时进行。严禁只移动了资源文件而遗留孤儿 `.meta`，或移动了资源未带走 `.meta` 导致 Unity 重新生成全新 GUID 进而破坏场景与预制体引用。

### 4. 关键文本文件的先读后改与保存
- **边界定义**：读取目标文件 ➔ 内存中生成新内容 ➔ 文本精准替换或全量覆盖 ➔ 校验写入完整性。
- **原子约束**：禁止盲写。修改前必须先读取确保内容一致；若写入遇到意外中断，必须具备自动恢复机制，杜绝把目标文件清空或破坏。

### 5. 实施版本号多端同步操作
- **边界定义**：实施交付时，工程实际版本 ➔ 需求台账总版本与条目版本 ➔ 各知识库文档头部版本。
- **原子约束**：必须在同一批次中原子性递增版本号，禁止出现“某些文档升版了而其他文档保持旧版”的异步断层。

## 🏛️ 三、必须做成原子性的【设计级清单】(Architectural Atomicity)

在编写具体业务逻辑、架构设计与 Unity 游戏玩法时，以下模块设计必须具备原子事务机制：

### 1. 本地游戏存档与配置持久化 (Save Game Transaction)
- **痛点风险**：直接向原存档文件写入时，若遇突然断电、闪退或存储已满，原存档文件瞬间损坏归零，造成灾难性死档；
- **原子设计标准**：
  $$\text{数据序列化} \longrightarrow \text{写入临时的 .tmp 文件} \longrightarrow \text{校验 MD5 或文件完整性} \longrightarrow \text{原子覆盖原存档 (File.Replace)}$$
  ```csharp
  // 伪代码标准原子存档范式
  public static void SaveDataAtomic(string targetPath, string jsonData)
  {
      string tempPath = targetPath + ".tmp";
      File.WriteAllText(tempPath, jsonData);
      // 原子替换：系统级原子操作，即使崩溃原文件依然完好
      if (File.Exists(targetPath)) {
          File.Replace(tempPath, targetPath, targetPath + ".bak");
      } else {
          File.Move(tempPath, targetPath);
      }
  }
  ```

### 2. 玩家经济系统与虚拟道具交易 (Economy & Inventory)
- **痛点风险**：网络延迟或代码异常导致“钱扣了但道具没进背包”，或重发包导致“道具重复刷出”；
- **原子设计标准**：
  - 扣除货币、添加道具、扣除物品格子、记录流水日志必须包裹在统一的 `TransactionScope` 或数据事务内；
  - 校验失败立即回滚（Rollback），严禁先扣钱再异步等待道具到达。

### 3. 有限状态机 (FSM) 的状态流转
- **痛点风险**：状态切换进行到一半发生异常，导致实体处于“既不是走、也不是跑、也没有待机”的无状态黑洞；
- **原子设计标准**：
  - 切换前先执行 `CanTransitionTo()` 守卫条件检查；
  - 校验通过后，原子化执行：旧状态 `Exit()` ➔ 指针赋值 ➔ 新状态 `Enter()`；
  - 若 `Exit()` 发生严重不可预期异常，需回退至明确定义的 `DefaultState`（如 Idle 默认待机）。

### 4. 关键网络 RPC 消息与帧同步指令
- **痛点风险**：网络丢包或重发导致相同指令执行多次；
- **原子设计标准**：
  - 每个请求附带单调递增的唯一事务序列号（Transaction Idempotent Token）；
  - 接收方先查重：已处理过的直接返回历史结果（幂等性），未处理过的原子化执行入库。

## 🛡️ 四、原子性落地准则与防破坏三步法

为了保证以上规范落地，所有涉及原子性操作和设计的实现，必须遵循三步法：

1. **【事前守卫 (Pre-flight Check)】**：在动手前，校验所有前置依赖（权限、文件是否存在、余额是否充足、网络是否通畅），任何一项不满足立刻停止，不做无谓尝试；
2. **【隔离执行 (Shadow Execution)】**：在影子区（如临时文件、内存缓存副本、未提交分支）中准备完整结果；
3. **【原子生效 (Commit / Swap)】**：通过单次原子替换（如指针切换、系统文件替换、单个 Git Commit）一次性应用结果；如遇失败，直接抛弃影子区，原系统丝毫不受污染。
