# 全文档中文化与通俗易懂表达规范 (Language Standard)

> ### 🏷️ **版本信息与实施追踪**
> - **当前文档版本**：`v4.16.0`
> - **对应实施版本**：`v4.16.0`
> - **版本治理规范**：遵循 [`rules/workflow/versioning_standard.md`](../workflow/versioning_standard.md)
> - **生效状态**：`[Release 稳定生效]`

本规范用于统一工程内所有文档、规则、注释、上下文压缩提炼、工具参数说明及会话答复的语言风格，保证所有人与智能体都能轻松读懂、准确执行。

---

## 🌏 一、全文档中文化要求

1. **核心交互与汇报**：
   - 所有的对话答复、执行汇报、状态提示，一律使用规范中文。
2. **工程文档全汉化**：
   - 项目内的 `README.md`、`docs/`、`rules/`、`templates/` 等所有文档，主要正文与标题必须使用规范中文。
   - 避免直接堆砌大段英文；如需引用英文专业名词（如 Git 指令、代码保留字、系统环境变量），应当使用中文说明其含义。

---

## 🎙️ 二、DSH 智能体执行全生命周期中文说明细则 (Full-Step Chinese Explanation)

在 DSH 的实际执行与工具调用过程中，智能体（Assistant）必须做到**全步骤、全旁白、全投射参数的 100% 纯中文说明**：

1. **工具调用前导交代 (Pre-Execution Explanation)**：
   - 在下发任何工具调用之前，必须向用户清晰交代即将执行的操作意图与动作，使用通俗中文短语；
2. **客户端 UI 投射参数 100% 汉化 (UI-Projected Localization)**：
   - **`bash` 工具的 `description` 参数硬门禁**：该字段直接作为终端卡片 (`TerminalCard`) 的标题投射在 DSH Web GUI 上。**坚决严禁使用英文**（如禁止传 `"Check disk space"`、`"Run test suite"`），**必须传规范中文动宾短语**（如“检测宿主磁盘空间与健康水位”、“运行自动化测试脚本验证”）；
   - **`subagent` / `subagent_fork` 的 `description` 参数**：同样必须使用规范中文（如“执行独立技术方案调研”）；
3. **步骤推进与过渡旁白**：
   - 在各工序切换时，使用中文清楚阐述当前进展、前置产出物以及下一步攻坚目标；
4. **结项与复盘交付**：
   - 交付物清单、AAR 三维复盘、效率看板指标一律使用纯中文输出。

## 🪞 三、上下文压缩与跨轮摘要同语种镜像守则 (Language Mirror Law)

在长会话运行过程中，宿主系统或智能体会自动生成历史检查点（Checkpoint）、压缩提炼摘要（Compacted Summary）或子任务交接快照。此时必须严格执行**同语种镜像保真**：

1. **绝对保真原则 (Language Invariance)**：
   - **输入是什么语言，压缩总结就必须输出什么语言**；
   - 用户与智能体前文对话为主导中文时，压缩生成的摘要正文、核心任务、关键概念、待办清单、问题排查**必须 100% 保持中文**；
2. **严禁语种突变漂移 (Anti-Drift Guard)**：
   - **坚决杜绝**将用户的中文讨论提炼成大段英文（如 `<compacted-summary>## Primary Request and Intent...`）；
   - 语种突变会导致后续交互中的大模型注意力受到英文 Prompt 干扰，引入理解偏差与阅读疲劳；
3. **压缩结构中文标准化模板**：
   当需要提炼长上下文时，必须采用以下规范中文骨架：
   - `## 核心诉求与意图` (代替 Primary Request and Intent)
   - `## 关键技术概念与机制` (代替 Key Technical Concepts)
   - `## 涉及文件与代码变动` (代替 Files and Code)
   - `## 错误归因与修复记录` (代替 Errors and Fixes)
   - `## 待办工单与后续步骤` (代替 Pending Jobs / Next Steps)

## ✍️ 四、通俗直白表达准则

为了杜绝理解分歧与阅读疲劳，行文必须做到以下三点：

1. **拒绝生僻字与生造词**：
   - 严禁使用冷僻字、罕见文言字词或生造的模糊概念。
   - 优先选择大众熟知、日常通用的词汇。
2. **句子短小，逻辑直接**：
   - 多用短句，主谓宾结构清晰，一眼能看出“谁在什么条件下做什么事”。
   - 避免多重从句和长段嵌套，每句话表达一个核心意思。
3. **少用学术黑话，讲大白话**：
   - 遇到抽象的技术概念，用简短生动的比喻或平实语言解释清楚（例如：将“幂等性过滤”解释为“避免重复执行，已经做过就不再重复做”）。

## 📖 五、常用术语中文对照表

| 英文/代码术语 | 推荐中文规范名 | 通俗含义解释 |
| :--- | :--- | :--- |
| **Crawling** | 信息抓取 / 状态感知 | 收集周围环境与文件信息 |
| **Indexing** | 建立索引 / 规范分类 | 将内容分类归档，方便查找 |
| **Query Understanding** | 意图解析 / 工单转化 | 听懂真正想干什么，转成明白的清单 |
| **Ranking / Precedence** | 优先级排序 / 规则仲裁 | 当规则打架时，先听谁的 |
| **Twiddlers / Safety** | 安全过滤网 / 终审拦截 | 临门一脚时的安全兜底检查 |
| **Serving** | 结果交付 / 格式呈现 | 把结果清晰明白地展现出来 |
| **De-duplication** | 查重过滤 / 避免重复 | 已经有的需求不重复建 |
| **Feedback Loop** | 闭环回溯 / 台账记录 | 改完后记得在账本里记上一笔 |
| **Compaction / Summary** | 上下文压缩 / 历史提炼 | 长对话浓缩总结，必须镜像输入语种 |
| **Tool Description** | 工具中文描述 / 卡片标题 | 投射在界面的中文动宾短语，严禁英文 |

## 🔍 六、语言风格自检清单

在提交任何文档、工具调用、压缩快照或答复之前，请对照自检：
- [ ] 调用 `bash` 等工具时，其 `description` 参数是否为规范中文动宾短语（绝无残留英文）？
- [ ] 执行过程的每一步交代与过渡说明是否为通俗流畅中文？
- [ ] 上下文压缩与检查点摘要是否与前文主导语言严格一致（严禁中文被压缩成英文）？
- [ ] 是否有大段未翻译的英文？
- [ ] 是否包含难以辨认或不常见的生僻字？
- [ ] 句子是否通顺流畅，普通人能否一眼读懂？
- [ ] 涉及的核心动作（如增加、修改、删除）是否明确指出？
