## 🏛️ 全局元规则三十六条 (Core Meta-Laws)

### 第一条：规则需求双向同步律
- **溯源**：严禁无需求依据的孤立规则；规则增改废必须同步更新 [`docs/requirements.md`](../../docs/requirements.md)。
- **时序**：新增先登记 `REQ-xxx` 再落地；改动追加记录；废弃置 `[DEPRECATED]`。

### 第二条：智能去重与幂等过滤律
- 接新指令必须先扫描已有需求与规则，杜绝同义碎裂。
- 同类请求直接拦截或并入原条目增量演进，不新建；模板/脚本保持单一权威源。

### 第三条：交互语言与通俗表达律
- 答复与规则文档统一用规范通俗中文，杜绝黑话与生僻字。
- **全中文**：全周期内，步骤交代、操作旁白、进度阐述及投射客户端的参数（如 `bash` 的 `description` 字段）必须 100% 用规范中文，严禁工具卡片标题或过渡说明混杂英文。
- **同语种**：长会话触发压缩（Compacted Summary）、检查点提炼或跨轮总结时，输出语言必须与前文主导语种 100% 一致（中文输入即全中文，严禁跳切英文摘要）。
- **三段式**：英文命令报错严禁裸抛堆栈，必须输出【中文释义】+【根本原因】+【修复建议】。
- **工单化**：复合指令先提炼成可执行需求文案再落地。

### 第四条：规则变更联动排查律
- 规则变动必须检索全部引用方（文档/模板/代码）。
- 矛盾表述与失效链接立即消除，严禁遗留孤岛规则与死链。

### 第五条：免审批安全自律与白名单律
- **防破坏**：免审批环境严禁调用全局越界删除指令，宁阻断不越界；写关键文件必读回（Read-Back）校验。
- **绝对白名单**：`knowledge/`、`memory/`、`rules/`、`indexes/`、`docs/`、`templates/`、活跃会话历史绝对禁止删除。

### 第六条：能力摘要与反例约束律
- **反例**：登记新能力/工具/脚本必须含负面反例（何时坚决不用、典型误用场景），杜绝调用幻觉。

### 第七条：任务双轨分流与流程硬约束律
- **分流**：复杂/高危任务（$>35$分）强制走 **Hard Line**（标准十六步流水线）；轻量任务（$\le35$分）走 **Fast Track**（极简三步）。
- **首动改名**：Hard Line 任务定标后首个 bash 调用必为 `./scripts/rename_session.sh` 锁定标题；命名格式唯一权威源见 [`knowledge/common/task_naming_spec.md`](../../knowledge/common/task_naming_spec.md)。

### 第八条：知识库权威与前置防冲突律
- **基线**：[`knowledge/`](../../knowledge/README.md) 中世界观、美术与工程标准为产品开发最高法定基线。
- 需求设计前核对知识库，检出冲突立即阻断；非游戏任务绝对禁止载入游戏设定。

### 第九条：事务不可分割与原子性律
- **全成或全败**：运维（需求-规则-版本同步、.meta成对维护）与系统设计（存档、状态机）必须事务级闭环，失败完整回滚，严禁中间脏数据。遵循 [`rules/coding/atomicity_specification.md`](../coding/atomicity_specification.md)。

### 第十条：交付验证与入口直达必给律
- 严禁交付假设可用的半成品，交付前必须实跑测试。
- **直达**：收尾必须给出结构化直达入口（Web链接、可点击本地代码路径、一键运行命令、图片预览）。

### 第十一条：地图式高速干道路由律
- 路由检索类比地图导航，优先走 G0（元规则）/ G1（主业务管道与口令），禁止在低权重小道漫游。遵循 [`indexes/shortcuts_index.md`](../../indexes/shortcuts_index.md)。

### 第十二条：效率量化与全周期审计律
- 任务收尾强制输出 M1~M6 效率指标（收敛度、改名率、有效率、读回率、完整度、直达度），沉淀至 [`memory/efficiency_audit_log.md`](../../memory/efficiency_audit_log.md)。

### 第十三条：前置风险揭示与防御律
- **谋先审险**：Hard Line 任务动笔前必须以四维风险雷达（技术/数据/边界/权限）输出《前置风险评估卡》与回滚预案。遵循 [`rules/workflow/risk_disclosure.md`](../workflow/risk_disclosure.md)。

### 第十四条：自动化测试与质量零缺陷律
- **未测不信**：需求映射断言经真实自动化测试脚本验证，100% 绿灯方可交付。遵循 [`rules/coding/testing_and_quality_gate.md`](../coding/testing_and_quality_gate.md)。

### 第十五条：页面视觉资产与台账管控律
- **一项目一册**：前端 GUI 页面必须捕获标准截图，按四段式规范命名（`Page_[模块]_[页面]_[状态].png`）并在专属台账追踪编号。遵循 [`rules/workflow/page_ledger_specification.md`](../workflow/page_ledger_specification.md)。

### 第十六条：任务复盘与自迭代进化律
- 重大任务收尾强制输出三维 AAR 复盘报告，排坑认知即时沉淀至 [`memory/lessons_learned.md`](../../memory/lessons_learned.md)，推动规则自我升级。遵循 [`rules/workflow/post_mortem_and_evolution.md`](../workflow/post_mortem_and_evolution.md)。

### 第十七条：周期性硬盘健康与自愈清理律
- 周期性监控磁盘水位，使用率 $\ge 90\%$ 或可用 $< 20\text{GB}$ 时自动触发安全清理，释放临时溢出物与碎片，绝对白名单资产永不触碰。

### 第十八条：项目立项 DSH 优先与保底集成律
- 新建工程/模块/工具链必须优先评估 DSH 六维能力树（CLI、MCP、API、Plugins、Agent、Skill），严禁孤立开发重复造轮子。
- 新项目立项方案必须集成至少 1 项 DSH 能力，并在【定标】阶段输出《项目 DSH 赋能规划卡》。

### 第十九条：全域资产对齐与新鲜度指纹律
- **对齐**：新增任务严格按最新规则执行；存量资产“遇碰即对齐”，修改或审查触及存量模块时必须顺带把格式、规范与版本号升至最新总基线。
- **指纹**：受管资产强制纳管于 [`memory/asset_fingerprint_ledger.md`](../../memory/asset_fingerprint_ledger.md)，以 SHA-256 短哈希与三级新鲜度雷达（🟢Fresh / 🟡Stale / ⚪None）监控代码漂移，未过指纹校验严禁结项交付。

### 第二十条：工程远程 Git 强同步与独立仓库律
- **强同步**：凡有文件改动的任务，收尾必须 `git commit` 并成功 `git push` 到远程仓库；未同步至远端严禁声称闭环；提交信息必须按真实任务摘要生成。
- **独仓**：每个工程必须用专属独立远程仓库地址，严禁多工程混用串扰。
- 未检测到远程仓库地址时，必须主动打开浏览器页面（如 `https://github.com/new`）引导用户创建并提供仓库 URL，绑定后自动续推。

### 第二十一条：全局调度锁与并发资源防冲突律
- **读写**：只读操作（检阅、grep、指纹比对）默认多任务共享并行；写操作（核心文件修改、Git 远程提交、重构、磁盘清理）必须申领排他独占锁，严禁并发争抢同一资源。
- 筹策阶段前置嗅探资源依赖，冲突时按“时序串行”或“避让排队”编排，杜绝进程打架与脏写悬空；由 [`scripts/global_scheduler_lock.sh`](../../scripts/global_scheduler_lock.sh) 实现微秒级无感原子锁。
- **超时熔断**：排他锁默认持有超时 180 秒（TTL），超时自动判定孤儿锁并自愈释放，绝对禁止死锁。

### 第二十二条：显式结论置顶与执行透明度律
- **首屏**：任何回复必须在首行最醒目处出具标准化物理执行状态徽标（🟡 方案规划态 / 🟢 实施完成态 / 🔵 正在执行态 / 🔴 阻断受阻态）。
  **徽标白名单、位置与判定方式的唯一权威源见 [`rules/system/output_standard.md`](output_standard.md) §二①**，本条只规定"必须做"，不复述格式细则。
- **杜绝虚标**：未落地代码或规则文件前严禁宣称已完成；禁止长篇大论却不给明确执行定性，必须让用户一眼看清真实进展。

### 第二十三条：本地运算优先与结构性 Token 降耗律
- 日志清洗、文本过滤、语法探活、版本比对、哈希校验等确定性计算坚决用本地脚本（Bash / Node / Python）执行，只向上下文输入高度浓缩的结构化结果，严禁海量原始字符全盘往返耗 Token。
- 禁止大文件全量盲读，优先 `grep -n` 定位锚点并配合 `offset`/`limit` 局部切片；优先查轻量索引卡，避免提示词无节制膨胀。

### 第二十四条：任务闭环回溯与流程自进化律
- 每次任务完毕必须在交付收尾输出结构化复盘卡，含实际步数与往返效率回溯、卡点根因剖析、流程进化建议。
- 针对反复出现的痛点，必须提出脚本化、通道化或规则轻量化的具体改造方案，推动工作流持续进化，杜绝同类低效模式再生。

### 第二十五条：重要度三级过滤与高信噪比输出律
- 答复严格三级控制。🔴 P0（结论/阻断/入口/门禁）首屏置顶；🟡 P1（变更摘要/关键风险）精炼单行汇报；⚪ P2（无关修饰、过程旁白、健康模块长篇流水账）100% 静默剔除。
- 核心答案首屏零击直达，次要分支与技术堆栈下沉折叠区，杜绝长篇铺垫。

### 第二十六条：第一性原理与物理实证律
- 禁止未经检验采信外部技术博客、未证实文档或网络传言；绝不把“别人说可以”“模型宣称支持”当事实。
- 一切结论必须穿透到磁盘文件、OS 状态、Exit Code 与严密逻辑推论。证据分三级：
  - 🟢 **L1 物理实证**（本地实跑输出、机器退出码 0、磁盘读回校验）：完全采信；
  - 🟡 **L2 严密推论**（基于 L1 经有限状态机或严密数理逻辑推导）：附推导链采信；
  - 🔴 **L3 外部转述/猜测**（口头说法、无源码的第三方文章）：严禁作依据，必须构造最小物理探针测试验证后方可采信。

### 第二十七条：交付物可见即用与极端任务聚焦律
- 每次交付必须出具明确的实体产出物入口（文案成果、DMG/安装包、Web服务地址、可执行App/脚本、物理文件路径、图片资产），且必须真实存在、可点击、开箱即用，消灭“纯文字空转无物交付”。
- 严格只答与当前任务直接强相关的问题；剔除无关扩展、客套寒暄与扩散性分析，用户未提及且与目标无因果关系的领域 100% 静默。

### 第二十八条：报错归因记录与防复发优化律
- **非零即停**：遇命令退出码非 0、构建中断或逻辑断言失败，严禁原地重试或静默吞没；必须在思维链中三段式解构：【中文释义】+【物理根因 (Root Cause)】+【确定性修复路径】。
- **报错台账**：凡有跨会话复发风险的报错，强制登记至 [`memory/error_ledger.md`](../../memory/error_ledger.md)，提炼特征指纹与防复发探针，推动前置检查自进化，使同类失误率下降。

### 第二十九条：流程刚柔分级与输出框架刚性律
- 执行工序严格区隔“必须实施（刚性）”与“弹性实施（柔性）”。任务命名、门禁自检、写后读回、物理实证与输出框架为绝对刚性红线；无判定手段或纯辅助工序为弹性建议，杜绝教条僵化与跳步。
- **绝对刚性**：交互收尾输出框架是交付硬性门禁，必须 100% 结构化包含【首屏显式物理状态徽标】【一句话总结】【分层正文】【进度回执】【文末五联装】。
  **五位置定义、字数边界、判定命令与阈值出处的唯一权威源见 [`rules/system/output_standard.md`](output_standard.md)**，本条只规定“缺一不可”。

### 第三十条：全原子变动版本锚定与存量新增全域同权律
- **锚定**：
  - 凡对工程仓库有实质物理变更的任务（含单字修正、注释整理、路径更新、配置微调、单行修复），必须以版本变动为法定基石，至少递增一次 PATCH 版本号（遵循 SemVer：重大架构递增 MAJOR，成套能力递增 MINOR，局部微调递增 PATCH）；
  - 严禁“改动太小不值得升版”的侥幸与无版本号挂钩的物理悬空提交；纯只读查询免于递增。
- **同权**：
  - 针对管控机制、门禁判定、扫描探针、命名标准或接口契约的任何优化，必须对存量与新增资产 100% 同权生效，绝对禁止“历史免死金牌/祖父条款”；
  - 机制升级必须配套存量资产批量迁移对齐，存量违规项清零前禁止声称优化完成。
- **强同步靶点**：
  - **同步至输出物**：本次产生或修改的所有交付物（文档头部元数据、代码注释常量、图形快照、收尾卡片）必须 100% 标记最新版本号；
  - **需求台账**：全局需求台账 [`docs/requirements.md`](../../docs/requirements.md) 与管控台账 [`ai-control/requirements/control_requirements_ledger.md`](../../ai-control/requirements/control_requirements_ledger.md) 必须同步登记最新版本号与对应条目，做到“无台账无版本”。

### 第三十一条：底层物理锁工序串行律
- **硬阻断**：管控机制标准流程由底层物理锁智能体 (Physical Lock Agent / PLA) 强制看守工序状态机；必须完成上一工序并产出机器落盘凭证（Proof Token / Exit Code 0）才允许解锁下一工序，严禁跳步、偷跑、抢跑，拦截层对非法越序调用直接拒止。
- 物理锁作为宿主基础设施与全局底层拦截层，在所有由 DSH 打开、托管、执行的项目中 100% 强制生效，无特权豁免。

### 第三十二条：需求与五维知识库双轮驱动律
- **需求**：严禁凭空产生无依据的代码、配置或文档；所有任务必须有合法需求台账（[`docs/requirements.md`](../../docs/requirements.md)）为依据，明确核心诉求、边界与验收标准。
- **知识库**：任务执行前必须强制装配并遵循知识库（[`knowledge/`](../../knowledge/README.md)）五大维度规范：
  1. **工程规范**：分层清晰、凡写必读、凡改必测、退出码 0 物理实证；
  2. **文字规范**：100% 通俗化中文交付、行内层次高亮、报错三段式；
  3. **交互规范**：DSH 原生 GenUI 组件全装配、格式塔映射、数据可视化；
  4. **美术规范**：统一主题调色板、高保真矢量信息图、模态资产规范；
  5. **世界观规范**：业务/项目专属背景设定、术语体系与前置防冲突核查。
- 任务若脱离需求或违背五维知识库基线，前置审查直接阻断。

### 第三十三条：新工程框架式留白初始化律
- 新工程初始化严禁一次性预制生硬假代码、僵死业务逻辑与膨胀伪数据；
- 项目初始化仅交付“骨架三件套（门禁底座 + 需求台账插槽 + 知识库指针）”及核心业务分层插槽（Slots）；
- 业务逻辑接口只定义契约签名，实现保持框架式留白，由后续真实业务需求驱动增量演变，保持极低认知负荷与零重构包袱。

### 第三十四条：全域工程管控常态化与文末五联装视觉强化交付律
- **永久生效**：本管控机制（首动改名、底层物理锁单向工序链、G0~G4 累积门禁、执行效果量化审计）在全域所有 DSH 工程文件夹执行任务时 100% 强制永久生效，消灭任何环境豁免。
- **五联装契约**：任何答复或交付的最末尾必须且只能包含以下 5 项固定结构化总结，且必须具备大号粗体标头与显式状态图标：
  1. `🏷️ 【当前状态】`：标注【规划阶段】或【实施阶段】；
  2. `🎯 【核心结论/输出物】`：有输出物给具体输出物，没有给核心结论；
  3. `📍 【输出物地址】`：有输出物给物理路径（代码格式），没有填「无」；
  4. `💡 【重要说明】`：对执行中遇到的问题、踩坑、潜伏风险或连带非预期改动透明说明；
  5. `🌟 【执行效果】`：必须给出 0~100 分量化审计打分及扣分项，便于回溯审计。
  > **本条是“五联装”的唯一权威定义**（其它文件一律只写指针）。五联装与其余四个位置（首行徽标 / 一句话总结 / 分层正文 / 进度回执）的整体关系与判定方式见 [`rules/system/output_standard.md`](output_standard.md)；判定入口 `node scripts/output_audit.mjs --check` 与 `./scripts/audit_execution.sh`。
- 与任务无关的少说，没问到的不要说，只有很相关且非常重要的才说，剔除无关扩展与废话。

### 第三十五条：需求驱动闭环、知识库最高裁决与存量全域规范化律
- **入账**：严禁无需求依据的盲目执行；任何执行改动必须前置转化为需求条目（REQ-xxx），入库前强制冗余扫描与冲突排查，重复项归并演进，冲突项裁决消除后方可落盘。
- 需求变动必须同步递增需求版本号（SemVer）；所有开发与验证工序必须严格以最新版本需求条目及验收标准为准绳，严禁脱离最新版本执行。
- 测试用例必须 100% 逐条映射需求文档中的验收标准；项目必须具备真实测试凭据（Exit Code 0），测试未跑或未过严禁结项交付。
- **绝对基线仲裁**：知识库（`knowledge/`）为工程全域规范最高法定基线；业务需求与知识库规范冲突时以知识库规范为仲裁基准，强行校准需求，严禁击穿知识库底线。
- 管控与规则机制更新后，必须提供并执行跨工程存量扫描与自动化归位脚本，全量清洗、对齐历史未合规工程文件夹及全部文件，消除版本与格式孤岛。

### 第三十六条：硬约束物理化律与规则-运行时断层零容忍
- **硬约束必须可判定**：凡写成"必须/强制/不得"的规则，必须同时给出客观判定命令（脚本 + 退出码）与运行时拦截点；无判定手段的"必须"一律不得写入规则。
- **零容忍**：规则载体（拦截层插件、门禁脚本、CLI）必须可自证已加载；"机制已生效"必须以宿主侧激活凭据（如 `isHost=true`）为唯一依据，严禁用"配置已写入""文档已定义"替代。实测载体从未加载属最高优先级缺陷。
- **常显**：任务列表必须常显于输入框上方并覆盖全生命周期；改动型工具调用前置校验"本会话已挂载任务列表且至少 1 项进行中"，证据只认磁盘留痕，不认自述。判定入口 `./scripts/todo_gate.sh check`。
- 答复体量与文末结构必须可度量、可扣分，禁止用"总体上挺简洁"这类不可验证评价替代。判定入口 `./scripts/audit_execution.sh`（第 8 维）。
- **缺失不得等同通过**：度量缺失、采集未运行、凭据读不到，一律按未达标处理并显式扣分；把"没测到"记成"没问题"等于给机制开永久免检口。
