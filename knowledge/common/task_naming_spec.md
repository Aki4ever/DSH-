# 通用任务命名规范 (Task Naming Specification)

> ### 🏷️ **版本信息与实施追踪**
> - **当前文档版本**：`v3.9.0`
> - **对应实施版本**：`v3.9.0`
> - **规范层级**：`【知识库 · 通用公共规范 · 命名唯一权威源】`
> - **需求依据**：`REQ-048`（需求一：任务命名规范统一）
> - **生效状态**：`[Release 稳定生效]`

本文档是**任务命名格式的唯一权威源**。任何位置提到"任务名怎么起""标题格式是什么"，
一律以本文档为准；其余文件（规则、记忆、脚本）只允许写指针，
**禁止复制本文档的格式定义**，避免同一事实出现两种说法。

---

## 🎯 一、三要素定义（本文档要回答的核心问题）

一个合格的任务名必须同时包含三样东西，缺一不可：

| # | 要素 | 在标题里的对应位置 | 取值来源 |
| :---: | :--- | :--- | :--- |
| **1** | **任务名** | 第一段 `[分类编号]` | 单字母业务分类 + 三位数字序号，见 §三 |
| **2** | **任务难度** | 第二段 `[难度分]` | 100 分制四维打分结果，见 §四 |
| **3** | **任务概述** | 第三段 `概述文字` | ≤ 8 个汉字的白话短语，见 §五 |

**一句话记住**：`[任务名][任务难度] 任务概述`。

---

## 📐 二、完整格式与硬性规则

### 1. 格式模板

```text
[分类编号][难度分] 汉字概述
```

### 2. 硬性规则（脚本逐条校验，不合规直接拒绝）

| # | 规则 | 正例 | 反例（必须被拒） |
| :---: | :--- | :--- | :--- |
| **R1** | **拼装顺序固定**：分类编号 → 难度分 → 概述，不得调换、不得增删段落 | `[R048][50分] 管控机制双优化` | `[50分][R048] 管控机制双优化` |
| **R2** | **分类编号**必须是「单字母 + 三位数字」 | `[R048]`、`[O002]` | `[R48]`（两位）、`[RR048]`、`[R0480]` |
| **R3** | **分类字母**必须在六类白名单内（R/F/D/S/O/Q） | `[F012]` | `[X001]`（字母不在白名单） |
| **R4** | **难度分**必须是 1~100 的整数且带"分"字 | `[75分]` | `[0分]`、`[101分]`、`[75]`（缺"分"）、`[7.5分]` |
| **R5** | **概述**汉字数 ≤ 8（数字、字母、标点不计入） | `管控机制双优化`（7 字） | `针对谷歌搜索引擎模型的研究与落地实践` |
| **R6** | **概述**不得为空、不得含换行、不得含 `[` `]` | `知识库重构` | `[]`、`重构\n换行` |
| **R7** | 整体必须**单行**，组件之间**不留多余空格** | `[R048][50分] 管控机制双优化` | `[R048] [50分]  管控机制双优化` |

> **为什么概述要限 8 个汉字**：侧边栏宽度有限，标题过长会被截断变形、遮挡时间戳。
> 该结论来自实测踩坑，详见 [`memory/lessons_learned.md`](../../memory/lessons_learned.md) 第 4 条。

## 🗂️ 三、要素一：任务名（分类编号）

分类编号标识任务归属哪条业务管道，沿用六大核心业务管道口径。

| 字母 | 业务管道 | 典型任务范畴 |
| :---: | :--- | :--- |
| **R** | **规**（规则） | 规则新增与修订、机制设计、治理流程 |
| **F** | **功**（功能） | 功能开发、特性实现、业务能力建设 |
| **D** | **文**（文档） | 文档编写、知识库沉淀、教学与图解 |
| **S** | **系**（系统） | 系统配置、环境治理、宿主与运行时 |
| **O** | **运**（运维） | 巡检、清理、监控、日常运行保障 |
| **Q** | **测**（测试） | 测试验证、质量审计、缺陷排查 |

**编号规则**：三位数字为**全局递增序号**，一旦分配即锁定，不复用、不回退。
序号与需求台账编号（`REQ-xxx`）**不必相同**，但同一任务应保持一致引用。

## 📊 四、要素二：任务难度

### 1. 四维打分模型（100 分制）

```text
难度总分 = 影响范围(0~30) + 依赖深度(0~30) + 安全风险(0~20) + 技术复杂度(0~20)
```

| 维度 | 满分 | 判读口径 |
| :--- | :---: | :--- |
| **影响范围** | 30 | 改动波及的文件与模块越多、越靠近核心，得分越高 |
| **依赖深度** | 30 | 前置依赖越深、联动排查面越广，得分越高 |
| **安全风险** | 20 | 越接近数据破坏、不可逆操作、权限边界，得分越高 |
| **技术复杂度** | 20 | 实现难度、跨技术栈程度、验证成本越高，得分越高 |

### 2. 分数与执行轨道联动

| 分数区间 | 执行轨道 | 说明 |
| :--- | :--- | :--- |
| **0 ~ 34 分** | ⚡ **快速轻量流**（Fast Track） | 极简三步闭环，免重命名与独立测试脚本 |
| **35 ~ 100 分** | 🚨 **标准完备流**（Hard Line） | 走完整标准闭环，含前置风险卡与审计卡 |

> 打分的**具体执行时机与轨道流程**，见 [`rules/workflow/task_execution_flow.md`](../../rules/workflow/task_execution_flow.md)。

## ✍️ 五、要素三：任务概述

| 要求 | 说明 |
| :--- | :--- |
| **长度** | ≤ 8 个汉字 |
| **文体** | 白话动宾短语，一眼看懂"这活儿在干什么" |
| **禁止** | 生僻字、英文缩写堆砌、标点堆叠、以"的"字长定语结尾 |
| **推荐** | `管控机制双优化`、`知识库重构`、`磁盘周期清理` |

**字数怎么数**：只数**汉字**。"管控机制双优化" = 7 字；
其中的数字、英文字母与标点（如 `v2`、`-`）**不计入**这 8 字。

## 🧪 六、正反示例对照

| 判定 | 标题 | 问题所在 |
| :---: | :--- | :--- |
| ✅ 合规 | `[R048][50分] 管控机制双优化` | 三要素齐备、概述 7 字 |
| ✅ 合规 | `[O002][25分] 磁盘周期清理` | 走快速流，概述 5 字 |
| ❌ 拒绝 | `[R48][50分] 管控机制双优化` | 编号非三位（违反 R2） |
| ❌ 拒绝 | `[X001][50分] 管控机制双优化` | 字母不在白名单（违反 R3） |
| ❌ 拒绝 | `[R048] 管控机制双优化` | 缺难度分（违反 R1/R4） |
| ❌ 拒绝 | `[R048][0分] 管控机制双优化` | 难度分越界（违反 R4） |
| ❌ 拒绝 | `[R048][50分] 针对谷歌搜索引擎模型的研究与落地实践` | 概述超 8 字（违反 R5） |

./scripts/rename_session.sh "[R048][50分] 管控机制双优化"
