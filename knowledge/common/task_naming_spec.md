# 通用任务命名规范 (Task Naming Specification)

> ### 🏷️ **版本信息与实施追踪**
> - **当前文档版本**：`v4.14.0`
> - **对应实施版本**：`v4.14.0`
> - **规范层级**：`【知识库 · 通用公共规范 · 命名唯一权威源】`
> - **需求依据**：`REQ-048`（需求一：任务命名规范统一）
> - **生效状态**：`[Release 稳定生效]`

本文档是**任务命名格式的唯一权威源**。任何位置提到"任务名怎么起""标题格式是什么"，
一律以本文档为准；其余文件（规则、记忆、脚本）只允许写指针，
**禁止复制本文档的格式定义**，避免同一事实出现两种说法。

---

## 🎯 一、三要素定义（本文档要回答的核心问题）

一个合格的任务名必须同时包含三样东西，缺一不可：

| # | 要素 | 在标题里的对应位置 | 取值来源 |
| :---: | :--- | :--- | :--- |
| **1** | **任务名** | 第一段 `[分类编号]` | 单字母业务分类 + 三位数字序号，见 §三 |
| **2** | **任务难度** | 第二段 `[难度分]` | 100 分制四维打分结果，见 §四 |
| **3** | **任务概述** | 第三段 `概述文字` | ≤ 8 个汉字的白话短语，见 §五 |

**一句话记住**：`[任务名][任务难度] 任务概述`。

---

## 📐 二、完整格式与硬性规则

### 1. 格式模板

```text
[分类编号][难度分] 汉字概述
```
*标准推荐示例：`[新需008][90] 管控机制优化`、`[调研002][45] 缓存方案选型`、`[优规012][80] 任务命名升级`*
*双轨兼容示例：`[R048][50分] 管控机制双优化`（向后兼容历史存量英文字母格式）*

### 2. 硬性规则（脚本逐条校验，不合规直接拒绝）

| # | 规则 | 正例 | 反例（必须被拒） |
| :---: | :--- | :--- | :--- |
| **R1** | **拼装顺序固定**：分类编号 → 难度分 → 概述，不得调换、不得增删段落 | `[新需008][90] 管控机制优化` | `[90][新需008] 管控机制优化` |
| **R2** | **分类编号**：中文分类（2字）+ 3位数字，或存量单字母+3位数字 | `[新需008]`、`[调研002]`、`[R048]` | `[新08]`（缺字/缺位）、`[新需求008]`（超2字） |
| **R3** | **分类类别白名单**：七大中文白名单（新需/调研/优规/修漏/重构/巡检/测验），兼容六大存量字母（R/F/D/S/O/Q） | `[新需001]`、`[修漏005]` | `[未知001]`（分类不在白名单） |
| **R4** | **难度分**必须是 1~100 的整数（可带"分"字或纯数字，100 分最难） | `[90]`、`[90分]`、`[1]` | `[0]`、`[101]`、`[7.5]` |
| **R5** | **概述**汉字数 ≤ 8（数字、字母、标点不计入，动宾极简） | `管控机制优化`（6 字） | `针对谷歌搜索引擎模型的研究与落地实践`（>8字） |
| **R6** | **概述**不得为空、不得含换行、不得含 `[` `]` | `知识库重构` | `[]`、`重构\n换行` |
| **R7** | 整体必须**单行**，组件之间**不留多余空格** | `[新需008][90] 管控机制优化` | `[新需008] [90]  管控机制优化` |

> **为什么概述要限 8 个汉字**：侧边栏宽度有限，标题过长会被截断变形、遮挡时间戳。
> 该结论来自实测踩坑，详见 [`memory/lessons_learned.md`](../../memory/lessons_learned.md) 第 4 条。

## 🗂️ 三、要素一：任务名（分类编号与语义化词库）

分类编号标识任务归属哪条业务管道，采用直观清晰的中文字义分类标识（2个汉字），一眼看懂任务性质：

| 中文分类 | 兼容字母 | 业务管道全称 | 典型任务范畴 | 正例 |
| :---: | :---: | :--- | :--- | :--- |
| **`新需`** | F | **新增需求** | 新业务特性、新功能开发、新增成套规约 | `[新需008][90] 管控机制优化` |
| **`调研`** | D | **探索调研** | 技术选型评估、可行性预研、行业方案对比 | `[调研002][45] 缓存方案选型` |
| **`优规`** | R | **规则优化** | 流程法典优化、门禁判定逻辑增强、契约完善 | `[优规012][80] 任务命名升级` |
| **`修漏`** | Q | **修复缺陷** | Bug排查修复、死链修正、脚本报错修补 | `[修漏005][70] 修复门禁未定义变量` |
| **`重构`** | S | **架构重构** | 跨层解耦、基础设施重构、规范瘦身演进 | `[重构003][85] 解耦执行与接口层` |
| **`巡检`** | O | **运维巡检** | 磁盘水位清理、系统新鲜度探活、指纹审计 | `[巡检009][20] 全库新鲜度探活` |
| **`测验`** | Q | **质量测验** | 自动化端到端测试、质量断言、沙箱逃生测试 | `[测验004][55] 插件自检用例补全` |

**编号规则**：三位数字为**全局流水序号**（`001`~`999`），一旦分配即锁定，不复用、不回退。
序号与需求台账编号（`REQ-xxx`）**不必相同**，但同一任务应保持一致引用。

## 📊 四、要素二：任务难度 (1~100 分自主打分法典)

### 1. 四维打分模型（100 分制，100分最难）

由模型在分析阶段（S04 双螺旋决策）根据实际工程复杂度自主评估打分：

```text
难度总分 = 影响范围(1~30) + 依赖深度/排查面(1~30) + 破坏风险/安全级别(1~20) + 技术实现复杂度(1~20)
```

| 维度 | 满分 | 判读口径与评分标尺 |
| :--- | :---: | :--- |
| **影响范围** | 30 | 改动波及的文件数与模块面，单文件(1~10)、模块内多文件(11~20)、全库系统级(21~30) |
| **依赖深度** | 30 | 前置依赖深度与全域联动排查面，无前置(1~10)、局部依赖(11~20)、全域深层联动(21~30) |
| **安全风险** | 20 | 数据破坏性、权限越界、不可逆改动，纯只读(1~5)、常规写入(6~12)、破坏性重构(13~20) |
| **技术复杂度** | 20 | 算法逻辑、跨技术栈编写、调试诊断成本，纯文字(1~5)、逻辑修改(6~12)、高精工程(13~20) |

### 2. 分数与执行轨道及难度梯队联动

| 难度分段 | 难度评级 | 典型特征与代表场景 | 对应执行轨道与约束 |
| :---: | :---: | :--- | :--- |
| **1 ~ 30 分** | 极低 / 低 | 仅修改 1~2 个文档、无逻辑代码改动、0 破坏性风险 | ⚡ **快速轻量流**（Fast Track） |
| **31 ~ 60 分** | 中等 | 多文件局部协同、单脚本增强、常规需求工单落地 | 🚨 **标准完备流**（Hard Line） |
| **61 ~ 85 分** | 较高 / 复杂 | 涉及核心门禁脚本修改、四级解耦层扩展、多仓库联动 | 🚨 **标准完备流**（严格跑双检全套） |
| **86 ~ 100 分**| 极高 / 颠覆 | 系统底层元规则颠覆、破坏性数据迁移、核心架构重置 | 🚨 **标准完备流** + 必须前置申领全局锁 |

> 打分的**具体执行时机与轨道流程**，见 [`rules/workflow/task_execution_flow.md`](../../rules/workflow/task_execution_flow.md)。

## ✍️ 五、要素三：任务概述

| 要求 | 说明 |
| :--- | :--- |
| **长度** | ≤ 8 个汉字 |
| **文体** | 白话动宾短语，一眼看懂"这活儿在干什么" |
| **禁止** | 生僻字、英文缩写堆砌、标点堆叠、以"的"字长定语结尾 |
| **推荐** | `管控机制双优化`、`知识库重构`、`磁盘周期清理` |

**字数怎么数**：只数**汉字**。"管控机制双优化" = 7 字；
其中的数字、英文字母与标点（如 `v2`、`-`）**不计入**这 8 字。
