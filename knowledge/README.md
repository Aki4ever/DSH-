## 🛡️ 一、前置防冲突核验硬性协议 (Pre-Execution Audit Protocol)

系统确立**“知行合一、前置核验”**的铁律：

```text
┌────────────────────────────────────────────────────────┐
│                   新需求提出 / 代码编写启动              │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│          【前置核验卡点】强制检阅知识库三大规范          │
│  - 剧情是否违背世界观？                                  │
│  - UI/视觉是否破坏美术基调？                            │
│  - 代码设计是否超出工程性能与架构红线？                 │
└───────────────────────────┬────────────────────────────┘
                            │
               ┌────────────┴────────────┐
               │                         │
        [存在冲突/设定违背]         [核验无冲突/完全对齐]
               │                         │
               ▼                         ▼
   ┌───────────────────────┐  ┌───────────────────────┐
   │ 🚨 强制阻断并即刻告警 │  │  ✅ 放行进入【攻坚】  │
   │ 驳回修改或提请专项演进│  │  精准实施并保持同步  │
   └───────────────────────┘  └───────────────────────┘
```

1. **执行前必查**：智能体在执行任何任务的【探境】与【定标】阶段，必须主动检索本知识库目录；
2. **零冲突红线**：新制定的需求文本、策划方案、游戏逻辑或美术表现，一旦与知识库已有条目发生冲突，**一律禁止强行写入**；
3. **变更须升版**：若确因业务迭代需要打破旧设定，必须在需求台账登记增量演进，并在修改知识库正文的同时，按规范原子化递增版本号。

## 🔄 三、维护与同步原则

1. **内容真实充实**：各子文档必须切实填写具体可落地的业务设定与规范内容，杜绝留白或泛泛空话；
2. **通俗易懂直白**：严格遵循通俗表达标准，消除无意义的生僻字与黑话；
3. **版本强同步**：所有知识库文档的变更，必须与需求台账（`docs/requirements.md`）和实际项目工程实施版本保持完全同步。
